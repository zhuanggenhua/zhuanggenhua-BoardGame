# 代码设计原则

本文件回答“代码结构该怎么设计、什么时候该用设计模式、哪些反模式必须避免”。它不替代 [`engine-systems.md`](engine-systems.md) 的共享引擎职责边界、[`shared-refactor-guard.md`](shared-refactor-guard.md) 的共享重构验收，也不替代 UI、测试、资源等专项标准。

## 何时查

- 新增或改写手写 TypeScript / JavaScript、React 组件、测试、E2E、项目脚本、devtools 或运行时配置前。
- 准备新增接口、抽象类、builder、facade、hook、adapter、selector、read model、manager、registry、pipeline、缓存或包装层前。
- 审查代码是否存在上帝模块、魔法字符串、复制粘贴、第二套真相、临时桥接层、过度接口、多职责测试套件或防护性架构时。
- 涉及共享引擎、transport、watchdog、recovery、flow、interaction 或 response-window 时，继续读 [`shared-refactor-guard.md`](shared-refactor-guard.md)。
- 涉及 UI 可见结构、玩家任务或画面元素职责时，继续读 [`ui-change-gates.md`](ui-change-gates.md) 与 [`ui-ux.md`](ui-ux.md)。

## 基本原则

- **单一职责原则（SRP）**：一个模块、文件、测试套件、UI 组件或服务只能有一个清晰职责和一个主要修改理由；同一文件不能同时承担规则结算、读模型、UI 表现、协议恢复、测试夹具和数据录入。
- **开闭原则（OCP）**：新增游戏、规则分支、响应窗口、AI 恢复、面板、配置项或测试行为族时，优先通过正式 owner、配置合同、registry、selector、adapter 或窄测试 helper 接入；不得让核心分发器、主 Board 或巨型测试文件持续追加特例。
- **里氏替换原则（LSP）**：同一接口、行为合同或测试 harness 的所有实现必须遵守同一成功、失败、时序、权限和恢复语义；调用方不能靠识别具体游戏、具体阶段、具体 adapter 或隐藏字段才能避免错误。
- **接口隔离原则（ISP）**：只暴露调用方真实需要的能力；不得把整份服务端状态、完整 socket / storage / engine config、整棵 UI 状态树或全部上下文对象传给下游。
- **依赖倒置原则（DIP）**：高层规则、UI、测试和工具依赖稳定合同、正式命令、selector、read model 或明确服务入口，而不是低层对象结构、临时字段、DOM 细节、socket 实现或旁路 helper。
- **迪米特法则 / 最少知识原则**：模块只和自己的直接 owner、直接协作者或正式入口交互；不得在多处穿透 `a.b.c.d` 式内部结构、复制状态解析过程或手写远端状态拼装。

## 项目补充原则

- **DRY**：同一规则语义、读模型、测试夹具、配置映射、资源地址或验证规则只保留一个权威实现；复制后微调默认视为职责边界问题。
- **KISS**：优先选择能解释当前需求的最小结构；复杂度必须换来更清楚的 owner、生命周期、验收点或扩展边界。
- **YAGNI**：不为“以后也许会用”创建空接口、空系统、空测试壳、预留状态、防重表、兼容壳或第二套恢复链。
- **单一真实来源**：作者源数据、运行时状态、表现投影、资源地址、训练记录、反馈状态、测试夹具和校验报告都必须有唯一 owner；派生缓存只能生成或校验，不能成为第二份真相。
- **测试按行为合同组织**：测试文件的 owner 是一个公开行为合同或行为族，不是“这个服务所有历史回归”。公共 socket、namespace、storage、engine config、训练记录器和断言工具应进入 helper；行为断言留在对应测试套件。
- **组合优先但不教条**：可替换规则、UI 子区域、游戏特化和测试场景优先组合；稳定身份关系和唯一 owner 可以用清晰领域对象承载。具体选择看职责归属，不看类名是否“像设计模式”。
- **新游戏先分职责再实现**：新 `gameId` 的设计稿、机制拆解和目录骨架必须先写清规则事实、正式状态、命令校验、事件生成、状态落地、派生读模型、UI Surface、测试夹具和素材数据各自的 owner；不得先做一个大 `game.ts` 或大 `Board.tsx`，再把后续拆分当成优化项。
- **主入口不是职责容器**：`game.ts` 只能做游戏注册、领域入口组装、系统接线和必要类型导出；`Board.tsx` 只能做页面组合、React 状态绑定、handler wiring 和子 UI 挂载。规则结算、命令分支、事件 reducer、数据 registry、读模型、动作列表、调试面板和可见 UI 子区域必须有正式 owner。

## 设计模式使用规则

设计模式只能解决已证明存在的职责问题，不能作为“看起来更专业”的默认架构。用了 helper、builder、facade、hook、adapter、selector、manager、registry 或 pipeline，不等于设计合格；只有它让责任归属更清楚、调用方知道得更少、变化集中在一个 owner 里，才算降低设计债。

| 模式 | 允许使用 | 禁止滥用 |
| --- | --- | --- |
| Registry / 映射 | 内容 ID、动作定义、游戏 manifest、文本 key、资源清单、面板入口等需要稳定查询和扩展时。 | 把运行时可变状态塞进 registry，或用 registry 替代作者源校验。 |
| Factory / Builder | 创建过程需要统一默认值、校验、生命周期绑定、资源注入或测试替换时。 | 只包一层构造调用，调用方仍要知道所有内部字段。 |
| Strategy | 同类规则存在多个可替换算法，且选择来源能由规则、配置或正式状态解释时。 | 为尚不存在的未来规则提前建空接口或空目录。 |
| Observer / Event | 已提交事实需要通知多个只读消费者，且订阅、注销和回放语义清楚时。 | 用事件隐藏命令顺序、状态写入或第二套结果解释。 |
| State Machine | 对象确实有互斥状态、显式转移、进入 / 退出动作和非法转移时。 | 用一堆布尔值、兜底分支和“如果异常就跳过”伪装状态机。 |
| Selector / Read Model | 多个消费者需要读取同一派生事实，且应隐藏底层状态结构时。 | 让 selector 执行命令、副作用、随机、持久化或规则结算。 |
| Adapter / Wrapper | 连接第三方 API、跨模块稳定边界、权限校验、回放记录、生命周期转换或短期迁移兼容有真实消费者时。 | 只转发方法名、掩盖旧职责没有重构、长期保留桥接层或第二套状态。 |
| Test Harness / Helper | 多个同类测试需要共享合法入口、夹具、事件读取和断言语言时。 | 把不同行为族的断言和场景藏进同一个巨型 helper。 |

## 反模式清单

- **上帝模块 / 上帝管理器**：一个文件同时拥有状态创建、规则结算、协议恢复、AI 决策、UI 展示、事件、存储、反馈、训练记录和测试夹具。
- **多职责测试套件**：同一测试文件混合公共夹具、传输协议、在线 AI 恢复、响应窗口、命令队列、反馈上报、训练记录和多游戏特化。
- **主 Board 变业务核心**：`Board.tsx` 同时承担规则推演、布局分支、CSS 细节、交互状态、截图专用状态和调试面板。
- **魔法数字 / 魔法字符串**：游戏 ID、动作名、阶段名、事件名、资源地址、状态字段、测试锚点散落在业务代码和断言里。
- **复制粘贴式编程**：复制同类规则、同类 Board 区块、同类测试场景或同类工具后改少量字段，导致修一处必须同步多处。
- **第二套真相**：配置包、运行时状态、表现层、反馈记录、训练记录、缓存、索引或测试夹具同时维护同一事实。
- **临时桥接层转正**：为了先跑通写的兼容层、中转层、包装层、影子状态、双命名兼容长期留在正式链路。
- **浅包装**：模块接口几乎等于实现细节，删除后复杂度直接消失，而不是回到多个调用方。
- **霰弹式修改**：一个小需求需要改很多不相干文件，说明 owner、扩展点或单一入口没有收口。
- **深层状态耦合**：业务代码、UI 或测试依赖固定内部层级、长路径读取、对象名猜测或复制状态解析作为正式依赖入口。
- **静默兜底 / 防护性架构**：内部不变量被破坏时返回假成功、自动修正、吞异常、fallback、预留冲突表或防重集合掩盖真正入口错误。

发现反模式时，先按通用裁决阶梯处理：不做、删除、审查现有职责、重构 / 迁移、改作者源 / 配置，最后才新增正式入口。需要架构深化时读取系统 `improve-codebase-architecture` skill。

## 体量触发器

行数不是根本问题，只是失控症状。商业项目可以有长文件，但长文件必须仍然是同一种责任的集中表达，例如生成数据、表格索引、单一算法或单一行为合同的完整实现。手写业务源码、主 Board、传输服务测试、规则运行时和 devtools 页面进入几千行时，默认需要证明它没有混入多类变化原因；进入万行级别时，默认列为严重设计债候选。

体量触发器不是一刀切失败线。若长文件确实仍是单一职责，可以加入白名单继续保留；白名单必须写在对应 owner 表、任务卡或设计文档里，并同时说明：该文件的唯一职责、为什么拆分会降低清晰度、明确不由它承载的责任、当前消费者、验证命令和下次复核触发条件。不能因为“暂时好用”“已有代码都在这里”或“拆起来麻烦”加入白名单；一旦出现规则结算、读模型、UI Surface、测试夹具、数据录入、协议恢复等多类变化原因混在一起，白名单失效，必须拆 owner。

| 手写文件行数 | 默认动作 |
| --- | --- |
| `801-1,500` | 确认当前文件是否仍只有一个变化原因。 |
| `1,501-3,000` | 新增大段逻辑、UI 或成组用例前先写拆分判断。 |
| `3,001-10,000` | 只允许紧急最小修复或明确的责任拆分；新增责任默认建新 owner。 |
| `> 10,000` | 本轮触碰时必须建立或引用设计债重构任务卡。 |
| `> 20,000` | 默认列为首批重构候选；除紧急最小修复外，先拆合同、消费者和验证路径。 |

新游戏首版比遗留代码更严格：`game.ts` 或 `Board.tsx` 超过约 `1,000` 行时必须先做体量审查；只有能按白名单条件证明它仍是单一职责入口时，才允许继续保留。`game.ts` 一旦开始出现大型 `switch` / 多类命令分支，或同时承担 validate / execute / reduce，必须先做白名单裁决；未通过时拆到 `domain/validate`、`domain/execute`、`domain/reducer` 或行为 owner。`Board.tsx` 一旦同时出现 UI、动作组合、读模型、教程 / 动画状态和调试面板，必须先做白名单裁决；未通过时拆到 Surface、read model、controller hook 或 UI 子 owner。没有完成拆分或白名单裁决，不能把 S1/S2/S5 或“新游戏基础完成”标为通过。

## 动手前自检

新增抽象、模式、测试套件或防护代码前，至少回答：

1. 这个职责的 owner 是谁，生命周期由谁开始和结束？
2. 状态写入口是否唯一，消费者是否只读？
3. 删除这个模块后，复杂度会消失，还是会重新分散到多个调用方？
4. 有没有当前真实调用入口和验收点，还是只服务未来想象？
5. 它是否和现有引擎、游戏配置包、UI 组件、测试 helper、浏览器 / Node 原生能力或依赖库能力重复？
6. 它失败时是内部契约错误、正常业务拒绝、外部输入失败，还是可恢复系统故障？
7. 测试覆盖的是公开行为合同，还是旧实现形状、内部字段和偶然调用顺序？

答不清时不得新增抽象。先回到职责归属、唯一写入口、作者源、正式入口和测试合同裁决。

## 重构验收

设计债重构完成时必须能证明：

- 原文件的现实责任变少，不再继续承担被拆走的 owner。
- 被拆出的文件按责任命名，有清晰调用方合同，不是按行号机械切块。
- 调用方知道得更少：不再到处拼内部字段、复制状态结构或理解恢复顺序。
- 公开行为不变；若行为变化，必须有用户、规格或规则合同批准。
- 旧入口、旧测试夹具或旧 helper 不再形成第二套真相源；确需临时 adapter 时写明现实依据和删除条件。
- 至少跑过覆盖该责任的最窄测试；影响共享层时按 [`shared-refactor-guard.md`](shared-refactor-guard.md) 选代表验证。
