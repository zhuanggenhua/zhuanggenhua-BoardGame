# E2E 与截图验收规范

本文件规定真实浏览器 E2E 和截图证据如何证明玩家可用合同。它不替代规则录入、素材 intake、UI 图面审计或用户开图；图面审计回到 [`ui-change-gates`](ui-change-gates.md) 与项目 [`ui-audit-loop`](../../skills/ui-audit-loop/SKILL.md)，用户开图回到 [`show-image-to-user`](../../skills/show-image-to-user/SKILL.md)。

## 适用边界

- 标准游戏 E2E 使用项目 Playwright runtime、fixture / 专用测试模式、最近真实入口和状态注入 / 代表态。
- **正常端到端与用户真实浏览器分层**：用户只说“正常端到端 / 重新端到端 / 走端到端”时，默认使用项目 Playwright runtime 和本文件的标准游戏 E2E 入口；不得擅自改走用户当前打开的浏览器、开发端口或真实手动会话。只有用户明确点名某个浏览器、端口、URL、设备窗口或真实环境，或本轮目标就是验证该环境下的自适应 / 兼容 / 线上分发问题时，该真实入口才成为对应专项的主证据。专项验证结束后，继续收口必须回到正常 E2E 主链；真实浏览器截图、诊断端口截图和手动会话截图不得混入正常端到端 PASS 图组。
- 明确游戏目标的 `e2e/<gameId>/...` 目标，启动测试服务前必须按游戏补齐本地缺失运行时素材；`--list`、共享目录和无明确游戏目标不得自动拉全站素材。
- 真实开房链路只在要证明房间创建、加入、座位、权限、联机同步、`setupData -> runtime` 或多端同步时使用。
- `dev:lite` 只能证明快速本地体验，不证明 API、认证、社交、后台、持久化或浏览器级端到端。
- 外部数据库只在认证、保存恢复、排行榜、后台、真实持久化兼容性等目标里成为验收对象；标准游戏 E2E 默认内存游戏服即可。

## 入口分层

- **最近真实入口优先**：游戏内流程、牌桌交互、HUD、动画、结算、刷新恢复、终局或复盘，默认从 game route / match route / 代表态进入，不从主页、大厅、建房机械起跑。
- **主页/大厅和游戏内流程分开**：前者证明入口漏斗、房间、路由和权限；后者证明具体游戏可玩性。除非本轮目标就是整条漏斗，不得绑成一条大 E2E。
- **“开局”指当前合同最近起点**：在游戏流程语境里，开局通常是已完成配置后的开局牌桌、首轮代表态或当前机制最近真实位点，不默认包含首页到进房。
- **V1 首页是大厅类默认入口**：游戏详情、素材包入口、创建/加入房间、下载/更新浮层等首页/大厅问题，默认从当前正式用户入口起跑；候选 HomeV2 / 预览页只能在用户点名或线上入口确实分发时作为主证据。
- **刷新、spectator、near-end、review 是独立合同**：这些链路默认单独建用例，从最近可注入代表态起跑，不挂在主流程后半段顺手证明。
- **视角必须显式**：依赖座位、私有信息、手牌归属、暗棋、权限或视角聚焦时，入口必须显式注入 `playerID` / seat / viewer identity；缺视角是测试入口错误，不能靠 UI fallback 掩盖。
- **默认值要真实**：用户未指定开启实验、偏好、调试或可选功能时，E2E 和截图必须使用产品默认值。若同时展示关闭态/开启态，文件名、截图名和汇报必须分支标注。

## 状态注入与玩家可见真相源

- fixture、代表态和测试模式只能构造当前合同需要的合法流程位置；不得为了让 E2E 稳定或截图好看，篡改玩家会看到的规则真相源。
- 玩家可见规则真相源包括角色属性轨、单位 / 怪物属性、牌面与持有物归属、牌堆 / 抽牌对象、地图实体、token、素材、正式状态标记、对象数量和胜负阈值。除非本轮目标本身就是验证这些对象的合法变化，否则测试不得改写它们来换取某个结果。
- 如果要稳定投骰、抽牌、翻牌、随机目标或随机结算，主路径是控制项目正式随机队列、骰子队列、牌堆顺序、低层 deterministic random，或用规则允许的代表态；不得转而改角色属性、怪物属性、牌面、持有物、素材或状态阈值。
- 如果目标确实需要让角色、单位或资源处于某个边界状态，优先用正式规则动作推进；必须注入代表态时，只能注入规则上合法的当前状态，并保留正式数据形状。禁止伪造超长属性轨、同值大数组、错素材、替代牌、隐藏临时状态或第二套测试基线。
- 规则交互已迁到 Choice Request、TimingOpportunity、响应窗口或其它正式玩家动作合同时，E2E 注入必须构造同一份当前可提交的玩家动作合同和 live interaction；只注入旧裸交互壳、缺候选命令的数据或历史兼容窗口，只能证明旧兼容路径，不能作为新交互验收或回归收口证据。
- 当截图、断言或 PASS 清单展示的 token、状态、资源、骰区、手牌或其它玩家可见对象来自 fixture、代表态、测试预置、harness state 替换或内部构造时，测试名、截图名、证据清单和用户汇报必须显式标明“预置 / 代表态 / 仅验证消费链”。禁止把预置出来的对象说成由当前截图链里的前一步规则动作自然获得。
- 如果本轮目标包含“对象从哪里来 / 是否实际获得 / 是否由某技能产生”，必须用正式玩家动作或规则结算产生该对象，并同时证明来源动作、对象出现和后续消费；预置状态只能作为分段合同，不能替代来源证明。
- 如果本轮目标点名“使用 / 消费某个 token、状态、牌或其它玩家可见对象”，完整 E2E 的主轴必须停在被点名的使用 / 消费窗口本身；对象来源只能作为前置合法性证据，不得把验收目标替换成相邻来源技能、相似效果、预置代表态或手绘 / 标注出来的 UI 对象。
- 黄金链截图中出现的玩家可见对象必须保留正式数据形状；测试断言应覆盖关键真相源未被夹具污染，例如属性轨槽位与当前位置、卡牌归属、牌型 / 符号、token 所在地、素材来源和胜负条件。

## 诊断与验收

- 修复前的 E2E、截图、几何测量和历史对照只能叫诊断 / 复现 / 对照，不能叫验收或收口。
- 验收必须发生在实际修复之后，并回到原始问题位点和最近邻未改分支。
- 入口图和完成图必须分开判定。角色 / 派系 / 可玩对象在选择页可见、能被选中、能进入牌桌，只证明入口合同成立；不得据此宣称机制实现完成、全面审计完成、新交互可用、进入实施中门槛已满足或发布级收口。
- 用户问“之前/原来/改前”时，必须先查旧提交、旧截图、旧 evidence、旧断言或用户提供的历史图；当前截图不能反推历史基线。
- 找错历史基线、错 worktree、错页面、旧 dev server 或候选图时，该证据作废，必须重锁入口和基线后再决定是否实施。

## 选择器与断言

- 选择器来自玩家可见语义、稳定 `data-testid` / `data-*`、ARIA、对象 id 或共享 helper；不得依赖临时 CSS、旧弹窗结构、测试占位文案或实现细节。
- UI 重构后同步审查操作路径、i18n 文案、断言和截图名；旧选择器仍能点到元素，不等于证明同一玩家动作。
- 断言必须直接命中用户目标。可滚动就要实际滚动并看见目标；按钮能用就要证明点击前权限态、点击后可见结果、源区/目标区变化；规则时序就要证明前后阶段。
- 测试语义不要写上屏。合法目标、来源、可移动、可攻击、己方/对手等语义通过隐藏测试锚点、ARIA、class、几何和截图核图验证，不在玩家 UI 里显示 debug 标签。
- 任何新交互或新 UI 都要进入覆盖矩阵：`新增项 -> 玩家动作/可见状态 -> 已有 E2E -> 需补 E2E -> 截图/断言证据`。已有 E2E 只有测试名、真实步骤、断言和截图明确命中该项时才可复用。
- 用户明确给出浏览器、端口、URL、设备或真实入口时，最终证据必须来自该入口。自启临时 dev server、固定 viewport、复用历史截图或换成测试端口，只能标成诊断证据；不能把它们汇报成用户指定入口已通过。若目标端口未运行，先说明现实后果并用项目正式启动命令启动或请求用户恢复，再回到同一个 URL 验证。
- **真实入口必须证明加载当前代码**：用户点名已有开发端口或真实浏览器入口，且本轮修改了前端、语言包、教程、样式、配置或素材索引时，E2E 开跑前必须先确认目标端口进程属于当前仓库，并证明页面已加载当前工作树。允许的最小证明是精确重启已确认归属的开发进程，或用页面文案、教程步骤、已删除 UI 不再出现、构建时间、关键断言等排除旧 bundle。若禁热更新、旧 dev server、浏览器缓存或截图仍显示旧步骤 / 旧文案 / 已删除 UI，当前证据全部降级为诊断，必须重启或刷新到同一 URL 后重跑，不能继续生成 PASS 图组。

## 真实操作与截图证据硬门禁

- **隐藏操作不得冒充独立玩家决策**：fixture、测试 harness、`evaluate` 内部派发、直接领域命令、状态替换、跳过 UI 的快捷函数，只能在第一步玩家动作之前构造合法起点，或压缩已经证明语义完全相同的重复操作。进入流程后，凡是玩家本应完成的独立点击、拖拽、选择、确认、关闭、切换或阶段推进动作，必须由真实页面控件、对象本体或设备等价输入完成。系统自动结算可以自动发生，但必须是产品运行时真实生命周期，而不是测试脚本代替玩家点击。
- **真实点击必须验命中区域**：当一个可见对象同时有主操作和次级检视 / 放大入口时，E2E 必须证明玩家点击命中的是对应真实区域：点对象本体时用坐标或 `elementFromPoint` 等前景证据确认没有点到嵌套图标、透明遮罩、教程浮层或测试锚点，并断言主规则结果发生且检视层未打开；点检视入口时同样证明命中检视按钮，断言只打开详情 / 放大且不改变选择、目标、费用、阶段或其它规则状态。只用内部 dispatch、`force`、子元素点击、状态直接改写或“结果最后变了”不能冒充真实点击。
- **多人教程不得越权验收**：教程主线以某个当前玩家视角验收时，E2E 不能通过切换 `playerID`、教程 `viewAs` 或调试座位去点击队友 / 对手回合里的移动、探索、确认、响应或阶段推进，再把截图命名为该当前玩家的自然流程。队友 / 对手若是教程前置，测试只能把其合法行动标成 AI / 系统按正式命令推进后的公开结果，或拆成独立视角章节证据；这些动作不能计入当前玩家的真实输入账本。
- **非流程悬浮工具可显式隐藏**：共享 FAB、聊天浮钮、调试入口、录屏控制等不承载当前游戏主流程、也不承载本轮验收动作的全局悬浮工具，可以在 E2E 中用明确样式或夹具隐藏/禁用命中区，前提是测试名、注释或 evidence 标明它是测试干扰项处理。不得用这条隐藏游戏 HUD、阶段按钮、手牌、地图、目标、确认入口、提示卡、放大入口或任何玩家完成当前流程必须使用的控件。
- **重复操作才允许压缩**：只有当多次操作的动作类型、承接对象、规则效果、权限条件和后续状态完全相同，且不会改变玩家对流程的理解时，才允许用批量输入、循环 helper 或代表态压缩；压缩必须在测试注释或 evidence 中列明等价依据。任何名称、目标、阶段、权限、成本、结果或下一步入口不同的操作，都不是重复操作。
- **阶段推进不得压缩**：每次“进入下一阶段 / 完成当前阶段 / 开始新阶段”的按钮或控件都代表一次独立状态转换，即使按钮外观、文案结构或调用函数相似，也必须逐次通过真实页面控件执行并断言前后状态；不得用一次点击、内部 dispatch、直接命令或批量 helper 代替多个阶段按钮。
- **隐藏独立步骤后的截图不是流程证据**：如果任意一个独立玩家决策或阶段推进被脚本、fixture 或 harness 隐藏完成，之后截取的画面只能标记为代表态/诊断证据，不能证明该动作可用，也不能放入“全流程端到端”或主黄金链截图包。被压缩的重复操作可以不逐次截图，但必须保留压缩前后的可见状态和等价证明；要证明独立流程，必须重跑并截取该动作之前、真实动作发生后和下一可操作态。
- **视口姿态截图可以直接设定但要标注**：当用户要的是“拖拽 / 缩放后的地图布局截图”而不是验证手势输入本身时，E2E 可以通过正式视口状态、测试姿态 helper 或一次性 DOM transform 直接设定地图视口姿态，避免脆弱鼠标轨迹模拟；但截图名、注释或 evidence 必须标明这是视口姿态设置，只能证明拖拽后画面布局、HUD 分层和坐标父层覆盖，不能单独证明玩家拖拽手势可用。若本轮目标包含“玩家能拖拽 / 缩放”，仍必须另有真实输入路径、共享视口组件测试或同入口交互断言覆盖。
- **每一步必须可回放**：端到端用例必须能列出 `玩家可见起点 -> 实际输入 -> 页面/规则结果 -> 下一步入口`；断言和截图逐步对应这张动作账本。只有状态变化、没有可追溯玩家输入的步骤，统一视为隐藏流程并按失败处理。
- **状态注入必须显式标注边界**：代表态注入要在测试名、注释或 evidence 中标明“仅用于进入起点”，并不得覆盖本轮要验收的交互、可见对象、权限或结果。若注入改变了这些内容，必须降级为代表态/分段合同，禁止继续命名或汇报为完整端到端。

## 默认浏览态与假控件

- 牌桌、棋盘、卡池、法术书、loadout 或配置库的基础流程 E2E 必须同时覆盖默认浏览态和规则操作态。默认浏览态证明玩家能检视对象、浏览集合和移动视野；规则操作态证明玩家能选择、计划、打出、提交或指定目标。只跑操作态不能宣称基本流程可用。
- 正面可见卡牌、角色卡、法术书卡、弃牌堆顶牌、场上卡和公开对象，除非规则明确隐藏或锁定，E2E 应点击或用等价输入打开详情 / 放大 / 规则回看，并断言放大层内容、关闭后回到同一页面、后续操作仍可继续。
- 图标、短标签、灰亮进度或数字叠层承担玩家必须理解的状态含义时，E2E 不能只读 `title`、无障碍文本或隐藏测试属性；必须通过 hover、focus、长按或等价真实输入让说明层进入前景，并至少截图覆盖每个不同含义的图标状态。若用户点名“每个图标 / 每个 tip”，则逐个落图并断言说明层未被裁切、未被遮挡、截图后能正常退场。
- 分类标签、筛选按钮、搜索、范围切换和分页若在画面可见，E2E 必须实际点击并断言可见集合、页码、排序、空结果或焦点发生对应变化；只断言控件存在、按钮高亮或 `aria-pressed` 变化不够。点击被父容器禁用、透明层遮挡或内容不变时，按假控件失败处理。
- 地图、棋盘、竞技场、长桌或房间网络如果设计上需要自由查看，E2E 必须实际执行拖拽平移、滚轮缩放或触控等价路径，断言内容 transform / 视窗状态变化、缩放读数或重置反馈出现，并抽查缩放后对象热区仍跟随同一坐标父容器。只截图静态地图、只断言底图加载或只用浏览器页面缩放，不能证明自由查看。
- 当用户点名成熟参考或项目已有同类成熟实现时，E2E 覆盖矩阵必须列 `参考已证明的基础交互 -> 目标对应断言 / 不采用理由`。若目标游戏缺少卡牌放大、筛选真变更、地图拖拽缩放等参考已具备的基础交互，且没有规则差异证据，不能写“端到端已跑通”。

## 对象级覆盖与代表链

- E2E 规范不默认要求“每张牌 / 每个对象都跑一条完整浏览器链”。逐对象完成口径先回到 [`description-to-implementation-audit`](description-to-implementation-audit.md)：每个对象必须有审计行，但证据层可以是直接浏览器链、共享流程引用、领域证据、Board 代表链或不适用。
- 同一机制族内多个对象若复用同一玩家入口、候选生成、命令 payload、执行入口、最终权威状态和清理语义，先建立共享流程审计行，再让对象逐项引用。只要差异仅是名称、图集、费用、数值、伤害类型、目标枚举或其它已声明的配置差异，就不得把它们自动升级成逐对象完整 E2E。
- 对象引用代表链时，evidence 必须写清：代表对象、共享流程、复用对象、判等依据、可配置差异、已有低层 / Board / E2E 证据、残余风险。只写“同类 / 同机制 / 复用 helper”不够。
- 下列情况才需要补该对象自己的直接浏览器链：触发时机不同、目标生成或权限不同、玩家入口不同、资源消耗不同、响应 / 可选 / 保密窗口不同、状态生命周期不同、最终可见结果不同、资源渲染路径不同且未被素材证据覆盖、已有证据冲突、用户点名要求该对象完整端到端。
- 若只是要证明某对象能进入同一个共享流程，优先补轻量入口断言或 Board 代表链；只有本轮验收要求“该对象完整端到端”时，才按玩家自然动作链补完整截图证据，不套固定六段模板。
- 禁止新增未定义的家族专用门槛词，例如把某个机制族笼统写成“全 X 逐对象浏览器链”。应写成可执行的证据缺口：`对象级审计缺行`、`共享流程判等缺口`、`某对象直接浏览器入口待补`、`主黄金链未纳入该机制` 或 `资源发布未回查`。

## 分支对照

- 同一组件、容器、hook、CSS 类或渲染路径服务多个模式时，目标分支和最近邻未改分支都要验证。
- 对照分支尽量复用同一测试文件、入口、视口族和代表态，只切换本轮相关参数。
- 目标分支要证明变化成立；对照分支要负向证明未被误伤，例如位置未漂移、按钮仍可点、保护槽位未被侵入。
- 缺对照时只能写“目标分支已验证，对照未完成”；不适用必须说明该分支不共享本轮改动路径或已有更窄合同覆盖。

## 黄金链

“全流程端到端 / 黄金端到端 / 黄金链 / golden flow”同义：同一个真实浏览器用例，从当前合同最近真实起点，连续推进到游戏结束、胜负收口或本合同收口点。

主黄金链只允许在第一步玩家动作前用一次正式 fixture / 代表态进入最近真实起点。第一步之后，所有独立决策、阶段推进和核心机制必须靠玩家动作、页面控件、合法系统结算和同一条命令链自然推进；仅对已证明完全等价的重复操作允许使用压缩 helper。不得再用 `injectCore`、TestHarness 状态替换、fixture 换段、手工改状态或领域命令跳过独立步骤。

不满足连续真实链的用例只能命名为 `桥接式综合候选链`、`组合验证链` 或 `分段合同链`。多条分段链、诊断链、代表态链或截图摘要相加，也不能登记为主黄金链。

进入主黄金链前，核心机制族必须先达到玩家可用合同：

- 规则状态与结算存在。
- 合法目标 / 输入路径存在。
- 正式 UI 可触发。
- 可见结果能解释。
- 非法或不可用分支有明确拒绝。
- 低层测试或窄真实入口 E2E 已证明。

未实现、未接 UI 或未证明的机制只能登记为 `deferred / 不在当前合同 / 分段或低层覆盖`，不能为凑长链塞进主黄金链。

主黄金链截图包必须按流程顺序编号，覆盖玩家动作前后、关键转场、结算结果和下一可操作态。截图要等画面稳定后落图：关键牌面、骰面、token、单位、阅读界面、响应窗口、结果面板真实渲染，无空白牌、加载骨架、遮挡浮层或未退场过渡层。摘要图、结果图、contact sheet 和少数代表图只能辅助导航，不能替代完整过程截图包。

教程提示、步骤卡或讲解浮层被其它阅读界面、详情层、结果层、放大层覆盖时，该截图不能作为教程证据。教程 E2E 断言必须证明玩家实际要读的教程卡在同帧前景可见；只断言教程 DOM 存在、文案存在、`visibility: visible` 或能点击，不足以证明截图合格。阅读界面 / 卡牌 / 结果层和教程卡需要同帧讲解时，至少用几何或 `elementFromPoint` 等前景断言覆盖关键教程卡，保证玩家截图里能直接看到教程提示。

stable / pre-push 前必须有覆盖矩阵，列出机制族、玩家主路径、真实浏览器覆盖、分段 / 代表 / 低层覆盖、`deferred` 项和外推理由。主黄金链最低覆盖当前合同内的核心回合推进、对象生成或揭示、不同对象类型、同类型至少两种交互形态、回合或阶段交接、随机 / 选择 / 目标指定、常用玩家交互族、胜负触发和收口点。常用玩家交互族包括当前游戏规则内高频出现的使用、交易 / 交换 / 转移、观察 / 视角切换、攻击 / 防御、确认 / 拒绝 / 跳过等；若某族不进主黄金链，覆盖矩阵必须标明它由哪条分段链、代表链或低层合同覆盖，并说明为什么不属于当前主链。

### 预算

- 单条 E2E 目标 `3` 分钟内；超过 `5` 分钟要说明价值并优先拆分；单文件接近或超过 `10` 分钟先拆主题。
- 同一问题长链最多重跑两次，总定位预算 `15` 分钟；拉到 `45` 分钟仍未锁定，停止堆长链，退回代表态、低层或组合合同。
- pre-push 只跑发生增量的非实施中游戏已登记主黄金链；`skipped` 或未命中用例名按失败处理。

## 桥接式组合验证

当完整玩法既要证明入口，又要证明 match 内中后段语义时，先判断能否用一条自然主链证明。只有当前合同同时包含彼此独立、不能稳定自然连续到达、或会把一个用例变成多合同混杂的目标时，才分段：

1. **入口合同链**：建房/入房、首个可行动回合、座位/权限/同步。
2. **中段代表态链**：本轮关心的 draw/discard、waiting、live/stacked、spectator、reload 等位点。
3. **终局前代表态链**：near-end、最后动作、review 前一跳、终局切换和复盘。

分段链只能说明“组合验证已覆盖这些合同”，不能自动说明自然流程已教完或主黄金链已通过。没有同一主链用例、核心机制被桥接跳过或承接态无法对上时，不能叫主黄金链。若同一用例同时想证明入口、中段、near-end、review、reload 和 AI 决策，默认已经超出单链合同，应拆并写明每个断点的必要性。

## 新游戏与流程节点

- 新游戏优先用自然主链证明从最近真实入口到首个可操作运行时，再按规则自然推进能到达的首个关键流程节点。只有终局、near-end、刷新恢复、旁观、多视角私密信息承载物或中后段复杂机制无法由同一主链稳定自然覆盖时，才拆分合同。
- **基本流程 E2E** 证明从最近真实入口完成角色/配置/开局确认，到达首个可操作运行时。
- **流程节点 / 终局 E2E** 只在确实需要分段时从已确认运行时代表态或 near-end 起跑，证明关键交互、结算和终局可见结果；不重复已由基本流程证明的前置，也不能伪装成自然主线的下一帧。
- 文件、用例和 evidence 分组必须写清 `natural-flow`、`basic-flow`、`first-scenario`、`near-end` 或 `endgame`，禁止一个“完整流程”承担多个独立合同，也禁止把分段合同包装成自然连续流程。
- 命中保护页时，先回到真实页面：刷新重试或重新加载，等测试 harness 与真实游戏页挂载；保护页截图不能交付。

## 阅读界面 / 私密信息 / 终局截图

证明规则阅读界面、事件书、任务书、阶段切换、阵营/角色手册或结局朗读时，截图必须证明规则流程，不只证明“有文字”。

最低截图组：

1. 公开揭示：应知玩家共同看到入口或结果。
2. 秘密阅读：不同视角看到不同阅读入口或内容，并证明不该看到的视角看不到。
3. 开局叙事：叙事正文可读，且发生在目标承接前。
4. 目标承接：读完后，目标、任务、胜负条件或下一步行动入口进入可操作界面。
5. 结局朗读：胜负条件达成后出现对应结果正文；只显示胜利/失败不算。

叙事幕、手册页、目标承接和终局统计必须分开。开局/结局叙事若声明为电影字幕幕或朗读幕，必须是独占阅读时刻，不得像普通弹窗、书页、统计报告或目标摘要卡。每张截图说明必须写清节点、玩家视角、公开/秘密、承接到哪一步。

分阵营、分角色或分权限的阅读界面必须分别截图：公开揭示后，至少证明多数/常规视角能看到自己该看的信息，少数/敌对/私密视角看见的是另一套合法信息，并证明不该看到的视角看不到。只截其中一方，或只截“阅读界面已打开”的通用页面，不能证明私密信息流程完整。

## 素材门槛

- E2E 不是素材 intake 或规则对象矩阵的替代品。新增游戏、继续接入或宣称基础流程闭环前，先确认规则对象素材矩阵和实现任务没有可本地推进的前置缺口。
- 规则明确存在的牌面、牌背、token、棋子、骰子、地图、帮助卡等对象，要么使用真实素材并完成语义命名、落盘、压缩、manifest 和运行时引用，要么明确标为阻塞。
- 页面仍使用未批准程序化替代、mock 图片、纯文字壳或错素材时，E2E 最多证明代码链路通过，不能升级为基础版完整闭环。
- 素材阻塞必须写清现实对象、真相源、当前候选、为什么不能落盘、下一步动作；不能用“后续美术优化”吞掉。

## 流程截图

- 完整端到端优先按玩家自然动作链截图；`触发前`、`亮相/翻出后`、`选择或随机前`、`选择/随机后`、`结算后`、`关闭/继续后`是常见证据角色，不是固定六张图、六个章节或六段模板。多个角色能在同一自然帧中同时成立时可以合并；存在独立玩家决策、阶段推进或可见结果变化时必须拆出前后证据。
- 若规则流程中存在方向、旋转、路径、目标、数量、顺序、模式、放置方式或是否执行等中间玩家决策，截图和断言必须分别覆盖候选出现、玩家改变或选择候选、提交 / 确认、后果出现。确认后结果图不能替代决策态截图；测试脚本也不得用内部状态替玩家完成该决策后再截图。
- 当最终结论涉及“全面审计”“当前范围已收口”“新角色 / 新派系实施完成”“从隐藏进入实施中”时，若新增对象包含新交互族、新状态消费、新按钮、新选择、新骰子 / 随机流程、响应窗口或新 UI 表现，最终验收截图必须是按交互族分组的有序截图组，不能只包含选角、房间、入口或静态识别图。
- 每个新增交互族的最低截图组是：交互触发前、交互出现、玩家选择 / 确认、结算结果、收口后可继续。若多个对象复用同一代表链，evidence 必须列共享流程判等矩阵，说明哪些对象没有逐分支截图、为什么可以共享、剩余差异由哪类低层或代表证据覆盖。
- 主黄金链截图必须覆盖完整过程，不是按机制族各挑一张代表图。每个关键动作至少要能看到动作前可操作态、动作后中间态 / 选择态 / 随机结果、结算结果、关闭或继续后的下一可操作态；连续机制之间要保留承接图。
- **主流程图组不得混入辅助证据**：教程、黄金链或其它按顺序交付的最终图组，只能包含同一条当前主流程里按玩家动作顺序产生的截图。基础布局验证图、拖拽 / 缩放姿态诊断图、移动端对照图、参考样本图、失败图、旧图、分段代表态或其它测试文件截图，不得占用主流程序号；确需保留时放到独立 evidence 分组或标为辅助证据。生成标号图和 PASS 清单前，必须逐张标明 `main-flow` / `auxiliary` / `diagnostic` 角色；任意相邻两张无法写出真实过渡动作或系统结算时，不能进入同一主流程图组。
- 教程、黄金链和其它按顺序交付的流程截图必须逐帧可追溯：相邻编号之间要有真实玩家输入、规则触发、系统自动结算或可见等待状态作为过渡，并在截图说明 / manifest 里写清。没有过渡动作或承接说明的相邻图，只能算分段代表态，不能登记为同一条端到端流程证据。
- **用户展示范围必须匹配验收范围**：用户要求查看某一步、某个分段或某组后续流程时，最终图组和 PASS 清单必须只覆盖该验收范围；全量截图包、诊断图、移动端对照图、失败图或无关代表态只能放到独立辅助证据里，不能混进用户验收图组。
- **分段图不得伪装连续链**：代表态、专题回归、视角切换章节和主线之间没有自然过渡动作时，必须分成独立证据组，或在用户可见索引 / 首帧把断点写成分段起点。只在文件路径、测试名或报告里标注分段，但把图组连续编号成自然流程，按“截图无效”处理。
- 玩家主动交互的过程图必须按真实操作顺序覆盖 `一级入口 -> 合法候选/目标高亮 -> 点击对象后的反馈或下一步 -> 提交/确认/拒绝 -> 结果落位/收口`。交易、交换、转移、使用、攻击、拾取、交付、观察和同类动作都适用；只截入口按钮或最终结果不能证明流程可读。
- 证据文档或任务状态必须形成四列闭环：玩家实际动作、自动断言、截图文件、用户目标对应。缺列只能登记为 `待补完整链路`。
- 过程截图文件名要使用可读顺序号和玩家动作 / 可见结果，例如 `01-开局牌桌`、`02-卖牌换CP后`、`03-进入投骰阶段`；禁止用内部状态名、fixture 名或代表图名替代流程节点。
- **动态截图的命名必须服从真实等待状态**：文件名写“命中”“伤害跳字”“结算”“恢复数字”等结果时，测试必须先等待对应的可见结果元素达到截图资格，再保存该帧；只等待动画容器、事件日志或最终服务端状态，不足以使用这些结果词命名。若只捕捉到来源唤醒或投射飞行，文件名必须如实标成对应过程帧。
- **反馈与目标必须同帧成立**：攻击、治疗、推斥、传送及其它带目标的动态效果，命中/跳字/落点截图必须同时断言目标本体可见、尺寸非零、没有被透明或遮挡到不可辨，并在同一采样帧保存原图；目标只在前一帧或 DOM 中存在而当前画面不可见，不能作为通过证据。
- **动态证据要区分阶段**：同一动作的截图至少区分来源出现、飞行/变化中、命中或结算；阶段没有被实际等待和截图捕获时，不能靠改文件名或复用旧图补齐。旧截图、旧标记图和旧 manifest 即使路径仍存在，也必须按当前运行、当前工作树和当前验收口径重新核验后才能继续作为 PASS。
- 写链前先锁规则时序家族，例如先选择后随机、先随机后选择、随机后直接结算、可选是否触发、翻出后自动结算；不能用一个家族的链路证明另一个家族。
- 规则源列出明确顺序时，截图动作账必须逐项对齐这些规则原子：揭示 / 翻出、候选或调整、玩家选择、提交 / 确认、自动后果、下一入口。若两个原子之间没有新的玩家输入，可以同帧截图并在说明里写清自动承接；若存在中间玩家输入，就必须有对应的真实控件操作和前后截图，不能用最终结果图、内部状态或重排编号补证。
- 完整链路必须来自同一规则链和同一对象。自然链和代表态混用时只能登记为组合验证或分段合同；测试名、截图目录、截图名和 evidence 必须显式写断点，不得让截图看起来像自然连续剧情。
- 无弹层的流程也要有收口图，证明高亮、临时状态、阻塞层或选中态已退场，主界面可继续操作。
- 展开/详情 UI 必须截图入口可见态和展开态；只截最终展开面板，无法证明入口链路。

关键机制的过程图必须证明“入口从哪里来、玩家怎么选、结果落在哪里”，不能只截按钮或最终状态：

- **物品 / 装备 / 结界 / 附件 / 能力使用**：至少包含使用前来源对象或持有区、选中后合法目标高亮、玩家点击目标或确认提交、使用后结果落位。合法目标高亮的颜色和形态遵循同一游戏已验收的对象语法，不强制绿色或实线，但必须清楚贴合目标本体并在整屏图里一眼可辨。附件、装备和结界若声明覆盖“打出到目标”，必须同时证明来源选择、合法目标高亮、玩家选择目标、附着或结算结果；只截最终附着关系不能证明目标选择链。结果落位必须能看见状态变化，例如生命 / 属性恢复、资源变化、物品移除、日志反馈、目标状态变化或下一步入口恢复。
- **视角切换 / 观察他人公开信息**：过程图和断言必须证明切换前主槽位 owner 是当前玩家，点击真实观察入口后同一持有区、装备区、手牌区、公开牌堆 / 弃牌或对应主槽位切到被观察对象，返回后 owner 复原，并证明旧观察面板、详情卡、辅助 HUD 或平行区域没有另起同类物品 / 牌堆副本；只截一个额外详情 UI 不能证明视角切换合同。
- **翻出后可选跳过 / 替代**：截图必须先证明玩家已经看见被翻出的房间、符号、牌型或将要结算的对象，再截图“是否跳过 / 是否替代”的选择。探索前声明、测试注入字段或只有跳过按钮的图，不能证明“知道类型后再决定是否跳过”。
- **攻击奖励 / 偷取 / 夺取**：截图必须同时证明奖励来源和奖励结果。最低过程是攻击前目标持有可偷对象、攻击或结算结果达到奖励阈值、奖励入口可见、选择奖励后对象归属变化；只截“偷取按钮”不能证明入口合法。
- **同类型不同交互**：黄金链声明覆盖某类对象时，至少两种不同交互形态要分别有过程图。例如同是房间或卡牌，一种自动结算、一种目标选择、一种可跳过 / 替代，不能互相用单张代表图外推。

## 随机、骰子与可介入结果

- 投骰、重掷、改骰、翻牌、抽牌、亮出事件、随机结果和阻塞式结算必须展示结果本体，不能只给日志、摘要、按钮或最终状态。
- 当测试目标是“让某个随机 / 骰子结果发生”时，必须优先控制随机或骰子结果本身；不能通过抬高 / 压低属性、改卡牌、改怪物数值或改阈值来间接制造同一结果，除非这些状态变化正是本轮要验证的规则动作。
- 可介入阶段必须覆盖：结果出现、可介入对象可见/选中、目标对象可选、介入后结果变化、确认后现实结果落位、收口后主界面可继续。
- 可直接点击真实骰子、卡牌、token、场地/区域格、地图格、单位或目标区域时，主路径必须点对象本体或投影命中区；数字按钮、文字列表和编号选项只能作备用/无障碍入口。
- 物理骰或 3D 骰必须证明真实可见渲染面存在、尺寸非零、骰体可辨、专用骰面和规则值一致，并等稳定状态后截图。通用 d6 内部映射不得外露成玩家语义。
- 重掷、改骰和同类随机介入不能只截“介入前”和“最终稳定后”。E2E 必须先断言新一次随机事件身份或重掷运动态，再保存至少一张过程帧；若过程帧只显示旧骰、静态骰或异常放大的骰体，不能用文件名写“重掷动画进行中”，必须修动画或等待条件后重拍。
- 多颗骰子必须逐颗可辨，不得叠成一团后用 DOM 数量或业务数组通过。
- 若规则仍允许重掷、改骰或介入，阻塞结果不能空白关闭；介入机会结束后再允许关闭并推进。
- 只有失败提示、toast 或门禁图不能替代成功路径证据。

## 视觉与动态证据

- 看图必须直击问题位点，逐项核对用户指出的区域、现象和目标；不能只扫整页。
- 证明布局、弹窗、HUD 或游戏进行页时，主图优先整屏/整牌桌，局部裁切只作辅证并保留原图路径。
- 正常端到端主证据必须是整页原图：凡用户要求“正常端到端 / 完整流程 / 黄金链”时，最终截图组的每一张主图都必须来自同一正常游戏入口的整页、整屏或整牌桌截图，能同时看见当前流程上下文、主操作区、玩家状态和下一步入口。卡牌、骰盘、弹窗或其它局部近景只能作为辅证，不能进入最终 PASS 图组，也不能用局部图替代流程前、真实操作后和下一可操作态的整页证据。
- 带序号或说明的交付图只能在原始截图外扩展画布或另建索引，不能把标注栏、遮罩、水印或说明文字压在截图像素上。任何覆盖原图内容的标注副本都不是“真实截图”，不得进入最终 PASS 清单或用户展示图组；已打开后被发现遮挡时，原 PASS 清单立即作废，必须重拍或重生成无遮挡图组。
- 局部截图不得冒充完整流程：测试脚本若使用 locator.screenshot()、裁切、局部导出或组件截图，只能在 evidence 中标为细节辅证；只要该局部图被当作“正常端到端”主图、PASS 清单图片或最终用户展示物，验收必须判为未完成并回到真实入口重拍整页原图。
- 满载/压力态优先：截图应包含会竞争空间的手牌、牌堆、玩家面板、阶段/资源、主按钮、当前 prompt、侧边工具、浮层入口、安全区等；缺项要说明原因。
- 翻页、移动、飞行、伤害飘字、结算跳分、展开收起等时间维度需求，必须有真实过程帧、动态证据或连续关键帧；最终静态图不够。
- 过程帧必须来自同一真实页面链路的运行时动画，肉眼能看出来源、飞行/变化、命中/结果和稳定态。DOM 节点存在、canvas 存在或截图文件落盘不等于视觉通过。
- 高亮/描边/发光必须在整屏图里让第一次看图的人一眼认出目标；靠读测试字段、局部放大或口头解释才看得出，判未达标。
- 截图里若目标对象被裁切、遮挡、只露边角、关键牌面空白、仍有过渡 ghost/骨架、页面出现 Vite/Chunk/模块加载错误，该截图不能作为最终验收。
- 移动端/PC 同构要对照同状态当前截图，不能只给移动端局部图；PC 一级信息在移动端要有明确去向或合理收纳。

## 截图来源与证据文档

- 截图必须来自当前问题场景、当前 worktree、当前入口；大厅页、预览页、兄弟入口、资源诊断页或 mock 场景不能替代原问题位点。
- **PASS 清单必须绑定当前证据运行**：展示清单的图片路径、测试结果、生成时间和代码版本必须来自同一次当前入口运行；若实现、等待条件、截图命名或验收口径发生变化，旧清单只能保留为历史/诊断记录，必须重建清单后才能打开或宣称 PASS。
- 证据说明必须写“我实际看到什么”和“是否达到本轮验收标准”；不要只复述断言、组件名、测试名或“正常”。
- PASS 清单必须把“来源已证明”和“消费链已证明”拆开记录。缺来源证据时，即使对象真实渲染、消费链通过，也只能标为代表态 / 分段合同，不得展示或汇报为完整端到端 PASS。
- 每张关键截图至少写 1-3 条肉眼观察结论，直接回应本轮需求点。
- 临时局部放大、标注图、流程图和 contact sheet 只能辅助；最终验收必须回到真实页面原图。
- 截图命名和汇报用玩家能懂的画面对象和动作，不用内部字段、测试夹具名或实现状态当画面名。
- 若最终回复写“E2E 通过 / 已验证成功”，必须给出已实际核对关键截图的完整绝对路径；窄入口验收至少 1 张，机制、交互或全面审计结论必须给出对应截图组路径与肉眼观察结论，否则不得用该口径收口。

## 用例拆分与命名

- 入口合同和游戏合同分文件优先：大厅/进房测试归入口主题；牌桌、终局、刷新恢复、spectator、AI roundtrip 归游戏主题。
- 每条用例只证明一个主合同。标题必须写清入口态、中间态、near-end、代表态、刷新恢复、分支对照或完整链路边界。
- 重复前置收成 helper、fixture 或代表态，不在每条用例里重复走长漏斗。
- 中文业务截图名优先；英文测试文件名可保留。面向用户的 evidence 目录和图片名不要默认用英文 slug，除非协议、工具或跨平台脚本硬性要求。

## 失败与收口

- E2E 用于收口，不作主调试器。先低层定位和修实现，再用最窄真实入口 E2E 收口。
- 环境不可用、入口打不开、目标状态无法构造、资源缺失或测试服务未启动时，停在该失败点，说明命令/步骤、现实后果、当前证据和最小补救动作。
- 测试输出 `passed`、trace 落盘、截图生成或断言变绿，只证明命令执行成功；最终结论必须回扣目标矩阵，逐项回答用户目标是否被证明。
- 看到不达标必须写不达标。E2E 绿灯不能覆盖手牌缺失、控件偏移、遮挡、只露边角、状态不完整、链路不真或截图无效。
