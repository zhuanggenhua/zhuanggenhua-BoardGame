# UI 改动门禁与验收入口

本文件只写 BoardGame UI 改动的项目级门槛：真实对象、规则/素材输入、主交互槽位、截图证据和返工条件。图面 `PASS/REVISE` 回到项目 [`ui-audit-loop`](../../skills/ui-audit-loop/SKILL.md)，用户开图回到项目 [`show-image-to-user`](../../skills/show-image-to-user/SKILL.md)，响应式细则回到 [`ui-responsive-layout`](ui-responsive-layout.md)，E2E 与截图证据链回到 [`e2e-verification`](e2e-verification.md)。

## 开工门槛

- **先锁四项**：问题对象、真相来源、真实入口/环境、验收口径。缺任一项，只能继续定位或补证据，不得改 UI。
- **点名范围冻结**：用户点名某张截图、编号步骤、具体 UI 位点或流程片段时，本轮问题对象只限该截图 / 步骤 / 位点，以及会直接遮挡、混淆或破坏该证据的同屏依赖。不得把同一图组里的其它截图、相邻 HUD、同类组件、顺手视觉优化、历史摘要待办或“看起来也能改”当成授权；发现范围外问题只作为备注或后续候选，除非先说明它如何让本轮点名目标无法验收，并采用最小必要改动。
- **点名对象类型不改写**：用户把问题点名到某个角色、卡牌、token、怪物、素材、房间或单个规则对象时，先查该对象自己的素材、配置、裁切、坐标、状态和真实截图；不得把它改写成通用 UI 设计、同类组件统一、全局布局密度或其它对象的问题后直接实施。只有证据证明该对象异常来自共享承载组件，才允许进入共享 UI 修复，并且必须说明会影响哪些同屏对象和回验哪些原始位点。
- **疑义先圈图确认**：用户用“密”“挤”“间隔”“上面”“下面”“不舒服”“不对”或类似空间 / 密度 / 视觉词点名 UI 时，只要对象、参照物或问题类型存在多个合理解释，先基于真实截图或原始素材生成红圈 / 框选诊断图，逐项说明“我理解的问题对象是什么、不是哪些对象”，并等用户确认后再改代码、样式、数据或测试。只有用户已经明确指出具体对象、具体改法和允许直接实施，或问题对象在当前画面中唯一且无需解释时，才可跳过圈图确认。
- **规则和素材是输入**：新增游戏主界面、桌面/棋盘/战场、规则对象、卡牌、token、骰子、角色板、设计稿或主 UI 重做前，必须先读取规则真相源和素材合同，列出会影响画面主体、布局、隐藏信息或操作入口的规则结论。
- **正式素材优先**：已有正式棋盘、卡牌、牌背、token、骰子、角色板或状态板时，画面主体必须由真实素材、正式 atlas crop 或已批准的程序化对象承担。缺关键素材时，先走资源补齐；不得用 HTML/CSS 壳、文字卡、占位图或错素材冒充正式对象。
- **素材比例必须保真**：正式素材进入 UI 后不得被拉伸、压扁、斜缩或用容器比例强行改形。卡牌、角色肖像、棋盘、token、骰子、提示板、阅读页和 atlas frame 必须按源图或裁剪 frame 的宽高比渲染；需要适配槽位时，用留白、裁切、缩放、`object-fit: contain`、等比 `cover` 或背景 frame 承接，但不能同时强设宽高把素材变形。若设计确实需要裁切，必须说明裁切语义和保留的主体区域；未经说明的比例失真直接按 UI 未通过处理。
- **规则物件不等于强制贴图**：读取规则和素材后先判定对象职责。身份物、可交互物、离散规则身份 / 状态类别标记、骰子、卡牌和隐藏信息优先使用正式素材或等价正式状态物件；连续数值或计数状态（例如伤害、生命、法力、资源）可以用该游戏已验收或明确批准的现代 UI 承载，例如进度条、本体覆盖层、贴宿主生命 / 数值读数或程序化组件，只要同源于规则状态、贴近宿主、可读且可验收。禁止因为规则里有 token / counter 就机械复刻物理 token 图；也禁止仅因对象是数值状态就默认放孤立角落徽章、圆形数字球、爱心 / 护盾等无正式来源的通用图标，或把守卫 / 护卫、行动准备、燃烧、眩晕这类会被规则引用的离散状态降级成普通进度条、脱离对象文本或通用 icon。
- **表现层异常不反改真相源**：截图、高亮、聚焦、点击命中或教程承接看起来不对时，默认先查消费链路。只有真相源自身、官方素材/规则、编辑器或两个独立证据能证明真相源错，才允许改数据、规则或素材索引。
- **设计稿阶段禁止实现抢跑**：用户要设计稿/视觉稿/效果稿时，当前交付物就是设计稿候选。用户明确人工批准前，不得启动真实运行页、扩展 Board/UI、用 E2E 或运行截图反推设计通过。
- **PC 主基线优先**：固定构图类游戏的 PC 桌面稿/桌面真实页是主基线；PC 未通过时，移动端只能记录风险和适配意图，不能作为整体完成证据。
- **大改先找来源家族**：整页/整区域布局、三处以上组件改动、主交互壳层改造或视觉体系调整前，必须打开真实参考代码、截图或设计系统条目，并抽取对象形状、位置锚点、状态语法、信息层级四类不变量；不得只写“参考成熟项目”。
- **同类视觉先对照成熟样本**：平台内已有通过验收的目标选择、高亮、反馈、生命 / 伤害读数或视角切换样本时，先对照其真实截图和实现，明确哪些不变量可复用、哪些因规则物件不同需要调整；复用成熟样本时必须同时复用显隐合同，例如默认 hover / 聚焦显示、用户用眼睛或等价视图开关切到常显，而不是只抄一个数字外观、改颜色、改测试名或按口头印象重画。
- **成熟参考先消费再新增**：平台内已有同类成熟实现时，必须先审查真实组件、真实入口 E2E 和当前截图，列出 `参考已具备 -> 目标是否复用 / 抽共享 / 不采用理由`。卡牌放大检视、卡池 / 法术书筛选、地图 / 棋盘自由拖拽缩放、视角切换、详情层这类基础交互若已有可复用组件或同构实现，默认优先复用或抽取共享组件；不复用时必须用规则差异、素材比例、输入模型或状态生命周期说明为什么共享会破坏当前游戏职责。不能另造一套缺基础交互的 UI 后只用局部 DOM 或操作态测试证明可用。
- **点名参考必须量化过账**：用户明确点名某个成熟游戏、页面、截图或组件作为参考时，不能只看交互结论或凭印象重画。开工前必须从参考实现 / 截图 / E2E 中抽出可执行参数：元素尺寸相对比例、命中区、默认显隐、hover / focus / touch 合同、z-index / 不抢主操作热区、关闭 / 返回位置、素材真实加载门槛和截图验收点。目标实现应复用这些参数或写清不采用的规则差异；缺少参考中已有能力时先补能力或抽共享，不得用“没有明确数字”自行随意设计。验收必须把关键参考参数写进断言、截图说明或 PASS 清单。
- **玩家任务与元素职责总账**：新增、重构或送验游戏 UI 前，必须把当前画面所有主要可见元素和交互状态列成总账：元素名称、唯一玩家任务、来源依据、默认态/候选态/选中态/确认态/结果态/收口态、是否复用成熟组件或统一视觉语法、退场或收纳条件、E2E/截图证据。用户连续指出同类 UI 问题时，下一步先补这张总账；不得继续按“指出一个按钮就改一个按钮、指出一个高亮就改一个高亮”的方式推进。
- **统一交互语法先过账**：同一游戏里语义相同的确认、取消、候选、选中、结果和等待状态必须复用同一个组件或同源视觉语法；若必须分化，先写出玩家任务差异和承接位置差异。组件复用不等于增加确认步骤，样式统一也不得改变规则授权、观看窗口或自动推进条件。
- **同层实体尺寸语义一致**：同一棋盘 / 房间 / 战场层里承担同等实体身份的玩家、怪物、单位或关键 token，应使用同一板面尺度或可解释的分档尺度；对象从独立放置变成被持有、附着或跟随时，不得无规则依据突然缩成另一种视觉层级。验收要同时覆盖独立态和附着态，证明主体可读、归属清楚且没有遮挡。
- **双边提案交互分层**：交易、交换、报价、援助、共同选择或其它需要另一方回应的流程，默认用一个方案区承载“发起方给什么 / 要什么 / 对谁”，用接收方回应区承载“同意 / 拒绝 / 反应”。横幅、顶部提示和教程卡只保留一行状态，例如“选择方案 / 等待同意 / 收到交易”，不得重复完整方案、不放第二个提交按钮、不把等待说明做成新的步骤面板；方案详情必须和提交、同意、拒绝或反提等实际操作放在同一操作层。只有规则确实要求公开讨论、共同确认或响应窗口时，才增加对应观看 / 回应确认，并写清谁在确认什么。
- **中间决策 UI 不得缺席**：规则要求玩家在翻出、揭示或生成对象后选择方向、旋转、落点、目标、数量、顺序、模式或是否执行时，UI 必须先展示对象本体、合法候选和决策控件，再提供提交 / 确认或自动后果。不能从“对象出现”直接跳到“结果已结算”，也不能用确认按钮的一句话替代候选态、选中态和可变反馈。
- **规则时序先于界面压缩**：当规则写明 `揭示 / 翻出 / 生成 -> 玩家调整或选择 -> 提交 -> 触发后果` 时，UI 必须在同一自然链里分别留下揭示态、调整 / 选择态、提交态和后果态。只有提交后的连续自动后果才允许合并到一个阅读区；玩家本应操作的中间控件不得因为面板空间、截图数量、教程合并或按钮样式统一而消失。
- **教程 UI 先整族审查**：教程点名某个 UI 交互族时，例如交易、使用物品、投骰、重掷、翻牌、确认、视角切换或目标选择，送验前必须把该交互族的 `入口 -> 候选 -> 选择 -> 确认/自动推进 -> 结果 -> 退场` 全链过账；不得只修当前被指出的按钮、截图或高亮。若同族已有其它样式、其它确认语义或其它截图链，必须同步裁定为复用、差异合理或删除/迁移，避免同一游戏长期保留多套玩家语法。
- **同批问题先收标准再实现**：同一轮 UI / 教程改动中，用户连续指出两个以上同类问题，例如确认语义、按钮样式、选中态、高亮、截图跳步、重复文案或对象分类，下一步必须先写清交互族标准和元素职责账，再继续改代码。该标准必须回答：这类交互什么时候出现、谁操作、是否需要确认、确认提交什么、结果在哪里显示、同游戏复用哪个组件或视觉语法、怎么截图验收。答不全时不得用局部 DOM、单张截图或单个按钮修复宣称收口。
- **主信息压缩必须证明收益**：HUD / 属性、手牌 / 候选牌、计划 / 装备槽、场上单位、当前提示和主动作入口属于玩家任务主信息；除非目标视口空间不足或用户明确要求压缩，进入选中、目标选择、教程、拖拽、确认或结算态不得自动切换成低可读小版。若确需压缩，E2E / 截图必须同时证明原主信息仍可读、被让出的空间确实改善当前主对象，而不是只证明“不挡住”。
- **同层级控件必须独立槽位**：同一可见层级、同一边角、同一工具带或状态带里的按钮、读数、开关和徽章，必须先分配互不重叠的槽位和间距，再渲染；不得让绝对定位默认值、层级提升、hover 态或展开态临时叠到同一坐标。地图缩放读数、生命显示眼睛、观察 / 返回、设置 / 筛选等同级工具不能互相抢占；验收要用整屏截图或可见矩形量测证明默认态、开启态和相邻工具都不相交且职责清楚。空间不足时按同一工具带重排、折叠或收纳，不能把某个同级控件挤进场景、HUD、手牌 / 法术书、资源或其它保护槽位。
- **多实体密排尺寸必须单调**：同一槽、同一格或同一队列按实体数量分档缩放时，实体越多只能越紧凑；少量实体不得比更多实体更小，也不能把“相等”当作已解决可读性问题。验收要同时覆盖相邻分档，例如 2 个与 3 个、3 个与 4 个，并用截图或几何证据证明低密度分档保留了更大的主体尺寸、更多实体分档没有溢出或遮挡。

## 交互模型

- **正式对象优先承接交互**：地图区、棋盘格、卡牌、单位、基地、token 等本体能点击/选择时，主路径优先点本体。按钮、列表、圆点、编号、隐藏锚点只能作无障碍、测试定位或已证明必要的备用入口。
- **默认浏览态也是真交互**：公开对象、地图区域和棋盘对象在非操作阶段仍承担浏览、检视、筛选或视角移动职责。除非规则明确隐藏或锁定，不能因为当前阶段不可执行某个动作，就把对象整体设成不可点击、不可聚焦或被父层 `pointer-events` 类禁用；浏览态至少要能打开详情、放大检视、筛选或给出清楚的不可用原因。
- **操作态保留次级检视入口**：对象在操作态已有单击主动作时，单击必须继续执行当前规则动作；若仍需要读对象、看图或回看规则，必须提供不抢主点击的次级检视入口，例如角落图标、右键、长按或等价无障碍入口。次级入口不得与选中态、禁用态或状态层互相变形/遮挡，也不得改变主选择、目标来源或提交状态；E2E 必须分别验证主动作和次级检视。
- **筛选控件必须真实改变集合**：分类标签、筛选按钮、范围切换、搜索框和分页控件只要可见可点，就必须改变可见集合、排序、焦点或已显示范围，并有选中态、空结果态和可恢复入口。父容器遮挡、透明热区吞点击、按钮只变颜色不改变集合、筛选结果不对应真实卡牌数据，均按假控件处理。若某筛选维度尚未接数据，应隐藏、禁用并说明数据缺口，不得作为正常控件展示。
- **高亮修正式能力**：已有正式高亮、描边、遮罩或可选态时，先修目标、边界、过滤、视角、样式和命中区。禁止新增标牌、气泡、圆点、按钮列表或说明壳层来掩盖正式高亮缺失/错位/难辨。
- **高亮必须清楚贴合**：先按同一游戏已验收的成熟语法和当前目标类型裁定主边界，不把某个游戏的颜色或实线样式升级成跨游戏硬规则。对象高亮可以是贴合本体的一层实线描边、背后描边、ring、发光、槽位覆盖或轻透明遮罩；关键是玩家第一眼能确认目标卡牌、token、棋子、头像、骰子、玩家板槽位或单位本体。不能用离边悬浮框、外扩定位框、CSS outline 或另一层大圆角框冒充贴合；多层光晕、阴影、脉冲、外圈描边和填充只能辅助一个主边界，不能形成双目标框，也不得压住、缩小、裁切或改形对象本体。截图中肉眼能看出高亮中心偏离目标本体、边框离目标边缘有间隙、圆角和本体不一致，或双层框让目标归属变模糊，直接返工。
- **候选态和选中态分层**：同一批可选对象必须把“可选候选”和“已选中”画成两种可区分但同源的状态。候选态只提示这里可以点，默认用底部短描边、边缘弱光、轻抬升或低权重边界，不得用完整套环、大圈、强发光或与选中态近似的主边界让玩家误以为已经选中。选中态必须升级为贴合对象本体的主描边、高亮边界或等价本体状态，并保留对象内容可读；不能用离体圆环、覆盖大圈或包住外挂按钮 / 角标的框替代已选中边界。涉及骰子、卡牌、token、棋子等重复小对象时，E2E / 截图至少分别证明未选候选态和选中态。
- **草稿结果进入目标槽位**：计划、准备、装备、编队、选择目标、分配数量或确认前草稿必须显示在它将要提交到的目标槽位 / 队列 / 对象本体上；卡面角标、小标签、计数 chip、按钮进度和日志只能辅助。验收要查目标槽位里可见真实对象、槽位序号或目标归属，不能只查源候选被打标。
- **可用性不冒充**：合法高亮、可点候选和主提交按钮只能展示当前状态下真实可提交的对象或动作；不可用对象应隐藏、禁用、灰置或说明原因，不得用绿色合法目标色、可点态或启用按钮让玩家误以为能提交。
- **区域目标和对象目标分开**：规则目标本身是区域、格子、边界或落点时，可以高亮完整区域或边界，并保留可点击命中区；规则目标是区域内对象、玩家、卡牌或 token 时，高亮必须贴合目标本体，不能用整格泛光冒充对象 / 玩家目标。
- **唯一候选仍需真实选择**：只要语义仍是选择目标、支付对象、骰子、卡牌、区域、单位或玩家，即使候选只有一个，也要走“对象高亮 -> 玩家点击对象 -> 系统结算”。只有完全没有目标、支付、顺序、数量、可跳过/可接受分支时，才允许自动推进。
- **一级动作与二级目标分层**：动作栏只展示当前规则态真实合法的一级动作。进入某个一级动作后，同级一级按钮退场，二级目标升到前景；一级按钮不得代点唯一目标，也不得和目标对象同屏并列制造多选错觉。
- **动作栏由规则态生成**：先列当前阶段合法动作集合，再渲染按钮；禁止用互不相关的布尔条件把按钮散落进同一动作栏。截图验收要核按钮数量和阶段规则一致，不只看按钮存在。
- **页面不能像卡死**：当前仍需玩家操作或等待重要系统阶段时，必须有显式状态化主入口、waiting 状态牌或等价锚点；不得让玩家只能靠猜桌面对象。
- **确认必须有授权**：确认/取消/提交只提交玩家已经完成的真实选择。确认前能改什么、确认后发生什么、为什么不能点对象直接完成，都必须能解释清楚。没有可撤销选择、多目标分配、费用选择、响应窗口、网络提交或危险动作时，常驻确认按钮是伪控件。
- **背景点击不得替代确认**：事件结果、发现牌、投骰/重掷结果、目标选择、支付分配、交易回应和其它关键流程浮层中，背景层只能拦截底层误点或关闭非关键检视层；不得提交动作、关闭结果、跳过观看窗口或代替继续/确认按钮。若按钮和点空白完全等价推进流程，按钮就是假控件，必须改成明确按钮提交或自动推进二选一，并用负向测试证明空白点击不会推进关键流程。
- **翻出后可选才弹决策**：跳过、替代、是否抽取、是否触发这类“先看类型/对象再决定”的分支，必须先让玩家看到已翻出的房间、符号、牌型或将要结算的对象，再在同一阅读区给出选择；探索前声明、顶部孤立按钮或只有按钮没有对象上下文的图，都不能算合格。
- **未发生结果不占主舞台**：规则结论若是没有抽牌、没有生成对象、没有结算事件或主动跳过，主舞台必须直接回到当前牌桌、下一步入口或轻量反馈；不得显示“未发生结果”面板、牌背、黑卡、空卡框、未来对象槽位、素材缺失壳，或已被跳过的触发符号/触发对象来冒充结果对象。
- **数量/分配是一个决策域**：数量、比例、分配额和是否拉满默认用一个数值控件加一个确认提交；不要拆成“跳过/转移/分配/确认分配”等近义主按钮，除非规则确实给出多个互斥动作。
- **按钮文案写现实动作**：确认、继续、返回、关闭、等待只写玩家正在做的现实动作；进度如“确认 0/3”可以保留，但不得写开发者流程、队列、步骤编号或内部状态。玩家完成对象、目标、数量或顺序选择后，最终提交按钮必须写成“确认 / 提交 + 对象”语义，例如“确认选择（2项）”，不得继续使用会让玩家误以为仍在选择的文案。
- **规则动作不加自造解释**：按钮触发规则动作时，优先使用规则动作短名或规则原文里的动作名；不要给按钮加“进行 / 执行 / 使用 + 状态标记”这类会改变玩家理解的解释。守卫、燃烧、眩晕、行动准备等结算后状态或标记，只能在结果态显示为状态，不得被动作栏命名成先点击的技能、目标或对象。
- **数值进度不重复翻译**：按钮、状态条和提示只要已经带有计数、比例、百分比、倒计时或阈值，就不能再用短状态词重复解释同一个数字的含义。短文案只写动作 / 状态 + 数字，例如“确认 0/3”“已确认 1/3”；不追加“其他玩家”“全部玩家”“还差”“剩余”“已完成”等可由数字直接推出的说明。只有没有进度数字，且阻塞对象不明显时，才在邻近说明里写清谁还没完成或差什么。
- **无差异信息不重复展示**：同一决策界面、候选比较界面、setup gate、摘要页或教程操作页中，若某组信息对全部候选或全部玩家完全相同，默认不在每张卡、每个席位、每个摘要块或外部 chip 中重复展示。例如生命、法力 / 魔力、护盾、初始资源、固定上限、固定规则提示、固定状态说明都只能在确有必要时用一个公共说明承载，或直接省略；玩家真正需要比较的差异项才进入候选卡、席位卡和摘要。若正式牌面 / 角色板 / 规则卡已经自带名称、费用、属性、类型或说明，不得再用外部 chip、短文案或摘要重复复写同一信息。运行时会动态变化、会影响当前决策或各对象确实不同的信息不按本条删除，但必须贴在唯一职责承载上，不得多处复本抢焦点。
- **提示 UI 不冒充承接物**：横幅、状态条、教程卡和提示气泡默认只告诉玩家看哪里/为什么；真实操作发生在按钮、对象、列表项或确认控件上时，文案和高亮必须指向真实承接物。
- **隐藏态不可发现**：弹窗、预览、菜单或临时层关闭后，内部按钮不得留在可访问树、Tab 顺序、role/name 或主文本流里；可保留容器壳，但必须禁用或不渲染交互项。

## 布局与空间

- **先建层级表**：涉及棋盘、牌区、持有物、主动作 dock、提示条、结算浮层、目标选择层或设计稿时，先写背景/规则空间/实体对象/主交互 overlay/结算 overlay/HUD 的层级、可重叠关系和保护对象。没有这三张表，不得开始布局。
- **当前主对象优先**：当前来源、目标、可执行对象、结算结果和阻塞下一步的对象必须在主视线区域；边栏、日志、摘要和右侧仪表盘只承接历史、详情或已结算摘要。
- **可读性高于几何通过**：不重叠、bbox 正确、元素数量正确只证明工程约束；玩家仍看不懂当前能点什么、结果贴谁、反馈在哪里，就判 `REVISE`。
- **满载空间要过账**：出稿前列出主棋盘、当前来源、当前目标、结算浮层、候选浏览、归档入口、玩家资源、临时提示的最大数量、最小可读尺寸、默认展开策略和让位顺序。没有空间预算，不得 AI PASS。
- **保护槽位逐项检查**：新增、移动、折叠、隐藏或删除 UI 前，逐项说明 token/状态/资源、生命/属性、阶段、骰盘、牌堆/弃牌堆、手牌、玩家面板、当前 prompt、主动作入口、日志/目标摘要等槽位是保留、避让、迁移还是不相关。
- **对象内部槽位也要保护**：新 UI 贴到卡牌、公共区对象、棋盘格、单位、场地/区域或玩家面板上时，先列该对象已有附属槽位，如状态 token、放大镜、短操作徽章、选中高亮和 hover 浮层；对象边缘不天然是空位。
- **token/角标不盖主体**：贴附 token、状态、撤离标记、角标必须贴近所属对象并可读，但不得压住牌面数字、规则文字、棋子本体或点击热区；多枚 token 用清晰序列排在对象外侧。token 优先承载离散规则身份、行动义务、保护 / 守卫关系、异常状态和可被后续规则引用的 marker；若某个 token 只表达连续数值或累计量，优先评估是否应迁到本体覆盖、进度条或贴宿主读数，避免为了保留物理 token 牺牲卡面可读性；未经同游戏成熟样本或明确设计批准，不得用孤立角落数字球替代这一裁决。
- **对象状态贴本体**：对象处于锁定、异常、可执行或其它规则状态时，优先在对象本体上用短状态条、角标或覆盖层表达，并保留对象主体可读。不得把对象缩成小图后在外部堆叠名称、归属和长状态说明；确需补充来源或归属时，放进 hover 标题、无障碍说明或一行弱信息。
- **多实体布局要验方向和尺寸**：同一格、同一槽或同一队列承载多个单位 / 卡牌 / token 时，E2E 不能只查对象存在或 owner 正确；必须证明排列轴、相对位置和最小可读尺寸符合当前游戏基线。若基线是上下排列，就要量上 / 下分离且相邻对象不能重叠；若基线是左右排列，就要量左 / 右分离且不能把对象压成不可读小片。任一实体因 lane、wrap 或压缩策略低于可读阈值，直接返工。
- **复合 lane 不能只验一个轴**：同一空间同时有“席位 / 阵营分区”和“同席位多对象排列”时，测试和截图说明必须分别证明 owner lane 轴、lane 内排列轴、owner 稳定性、最小可读尺寸和容量不足时的 overflow 策略。只证明左右分区、只证明上下排列、或用一个 `vertical / horizontal` 标签同时代表两层语义，都不能判通过。除非当前游戏规则或成熟同类 UI 明确采用叠牌语法，测试不得把负 margin、absolute 叠放、transform 错位或只露角的“可点击区域”当作上下排列通过证据；若基线定义了每列容量，E2E 必须断言列数、每列数量、同列不重叠、跨列不重叠和无操作浮层遮挡，容量不足再证明滚动、分页、展开或焦点检视可访问。
- **HUD 不挤压主布局**：等待、响应、确认、短提示、viewport loading 等动态 UI 使用 overlay、fixed、absolute、HudPortal 或稳定 HUD 槽位；不得插入正常文档流把手牌区、右 rail、棋盘、骰盘或主按钮顶走。状态 / 属性 / 提示卡这类常驻 HUD 若有可用角落、侧边或上方锚点，不得长期占用同一底部网格列并压缩当前可支配对象集合；移动前后要证明 HUD 本身仍可读，手牌 / 候选牌 / 计划槽位获得了真实空间收益。顶层 HUD 锚点不得由棋盘实体、底图内容或场景缩放位置驱动；HUD 外壳、提示卡背景、数值底纹和纯视觉承载默认不吃输入，只有放大镜、眼睛、关闭、切换、提交等自身真实控件命中。若 HUD 与当前来源、目标、可选对象或主操作发生冲突，先按层级职责处理：同层 HUD 重排、临时折叠 / 透明、当前目标提权或收纳非当前信息；不得用低层场景实体是否存在来横向漂移 HUD，也不得用几何不相交代替玩家任务和点击命中验收。验收必须用 `elementFromPoint` 或等价真实命中链覆盖被 HUD 视觉覆盖的当前对象：对象主体点击点应命中该对象或其主操作，不得命中 HUD 提示卡、属性底纹、透明热区或测试旁路。
- **机制详情默认收纳**：机制性、可选详情或状态汇总 UI 不得常驻挤压、覆盖或抢占核心牌桌对象，例如基地、棋盘、手牌、牌库 / 弃牌、玩家面板、当前 prompt 和主动作入口。此类信息默认放到中性 HUD、工具入口、可展开抽屉或弹层；公开机制汇总不得借用私有牌堆、抽牌堆、弃牌堆、手牌或具体对象槽位作为入口，除非规则动作本身就是从该对象发起。用户指定入口位置时按用户裁决。展开态必须可关闭，且不得替换、挤压或永久遮挡核心 UI；如果临时浮层会覆盖局部牌桌，验收截图必须同时覆盖入口态和展开态，并证明玩家能找回被收纳信息。
- **底部主交互贴边**：手牌区、持有区、主动作栏和底部 rail 默认贴近牌桌/屏幕边界并让位给对象本体。无语义空白必须说明职责；说不清就未达标。
- **响应式改动不降级主信息**：涉及桌面压力态、手机横屏或其它响应式布局时，先回 [`ui-responsive-layout`](ui-responsive-layout.md) 裁决壳层、锚点和承载量。截图验收不得把整层缩小、减少卡牌 / 槽位数量、压小 HUD 或主操作区当作遮挡修复；必须证明核心对象数量、可读尺寸、底部 / 边缘空隙、关键主对象未被 HUD 遮挡，以及相邻区域不相交同时成立。
- **视角切换复用原槽位**：观察队友、切换席位、查看对手或切到其它角色视角时，角色板、属性、公开牌堆 / 弃牌、持有区、手牌 / 装备区等已有主槽位必须直接切换数据源或明确进入只读态；不得在观察面板、详情卡、toast 或辅助 HUD 里另建同类物品 / 装备 / 牌堆 / 状态副本来证明“能看见”。新增任何平行 owner UI 前，必须先回答：这是原主槽位切 owner 后仍不可承载，还是规则真的要求双方公开信息并列比较；答不出就删除平行 UI，回到视角切换。
- **决策按钮贴近承接区**：玩家读完一个弹层、翻出结果、对象详情或目标选择说明后才按的按钮，应放在该承接区下方或主操作 dock，且截图要能看出按钮控制的是当前对象；不得放到远离阅读路径的顶部角落，除非它只是关闭/返回。
- **固定牌桌不靠页面滚动**：除非规则或用户明确允许长桌/滚动战场，桌面进行页应在 `1920x1080` 首屏看见完整主状态；放不下先调比例、留白和非核心装饰。
- **地图 / 棋盘视窗可自由查看**：地图、棋盘、竞技场或长桌内容大于视窗、会被玩家状态 / 手牌 / 计划区 / 主动作栏等界面对象遮挡或裁切，或需要查看局部细节时，必须提供玩家可发现的自由拖拽 / 滚轮缩放 / 触控缩放能力，并保持格子、热区、实体、特效和底图在同一坐标父容器。已有共享视窗能力时优先复用；自行实现必须覆盖拖拽阈值、拖拽后抑制误点击、缩放锚点、边界策略、触控手势和缩放读数。默认概览态可以按完整场景缩放到真实视口和底部界面对象之内，以保证全部区域可见且不被玩家状态、手牌 / 法术书、计划区或主动作栏遮挡；这只是相机初始值，不得变成内框、固定比例壳或 UI 摆放范围。验收不能只看变换值变化；默认态证明全部区域可见、界面锚点贴真实视口且无内框，放大 / 拖拽态证明视窗占据真实地图层、放大后的场景内容覆盖视窗、横向和纵向都能产生可见位移且对象热区跟随同一坐标层；若某类场景确实只能单轴查看，必须有规则、视口形态或内容尺寸证据并写进验收说明。不能只靠页面滚动、浏览器缩放、开发调试入口或固定缩放比例冒充自由查看。
- **边缘对象单独验收**：靠边卡牌、棋盘格、头像、牌库、最外侧对象要确认主体完整、未被父容器/遮罩/截图边界裁掉、外缘无异常透明框或脏边。
- **骰盘不是通用弹窗容器**：骰盘只承接骰子本体、选骰、改骰、重投和骰盘确认；卡牌响应、目标选择、结果比较、让过提示等需要独立主舞台/HUD。

## 样式与回归边界

- **样式任务默认不改功能面**：调间距、字号、颜色、圆角、阴影、遮挡、密度或响应式表现时，默认只改呈现；不得顺手删除/隐藏/替换入口、改默认状态、改触发路径或改信息默认可见范围。
- **样式微调先锁不变量**：动手前明确滚动语义、列数、对象尺寸、主内容宽度、主按钮位置和关键控件位置哪些不能变。
- **视觉尺寸不机械补测试**：尺寸、坐标、密度、间距和可读性这类视觉 bug，默认回到真实截图、人工图面判断、现有最窄检查或临时 evidence；是否新增阻断测试由 [`testing-tdd`](testing-tdd.md) 裁决，不得把“发现一个 UI bug 就补一个测试”当成 TDD 或默认收口动作。
- **样式问题不升级布局**：用户只反馈视觉装饰时，只在现有槽位内改；若确需动布局，先说明原始症状、布局根因证据、改动范围和修后回验位点。
- **新交互按新 UI 验收**：只要改变玩家发现候选、浏览/筛选、判断可操作对象、选择、确认提交或视图切换方式，即使代码上只是“小改样式”，也按新 UI 执行真实入口 E2E 和截图验收。
- **原始 UI bug 不用旁路收口**：用户反馈现有位点可读性、显隐、点击状态、缩放、遮挡或对齐时，目标是修原位点。未经用户明确要求，不得新增 HUD、toast、辅助面板或另一套显眼组件来替代。
- **反馈动效不扩写成面板**：治疗、伤害、资源变化、抽取和控制权变化若以飘字 / 跳字承接，玩家可见层只显示绑定对象的短反馈；属性列表、原因、日志详情和审计文本进日志、详情或无障碍说明，不得把飘字扩成两行结果面板。
- **回归恢复先锁旧合同**：用户要求恢复原来样式/逻辑/默认关闭态时，先找 last known good 代码和截图，优先恢复旧实现或等价抽离；不得凭旧图重画一版“像以前”的 UI。
- **开关两分支要隔离**：默认关闭旧体验和开启新体验都属于正式面。两者若视觉、布局锚点、动画或交互语义不同，应拆独立分支/组件/样式入口；不得用同一组件 props 拼出两份合同后宣称恢复。
- **删除可选 UI 不删共用合同**：清理可选分支、实验模式、调试入口或高级渲染前，先分清可选分支专属职责和默认态共用职责；共用素材加载、旧动效、尺寸、命中区、锚点和测试合同必须保留或先迁移。

## 证据与验收

- **截图验收只在稳定候选触发**：稳定交付候选、完整重构收口、用户要求截图/看图/玩家视角检查，或测试过但 UI 风险高时，才进入正式截图审计。过程性搭建只做匹配风险的功能验证，不能宣称视觉 PASS。
- **验收范围冻结**：截图、动态证据、AI 图面裁决和用户开图只覆盖本轮目标及直接影响面。范围外问题只列备注，除非它遮挡目标或让证据无效。
- **截图先锁真实入口**：取图前确认 URL/路由、工作区/文件路径、端口进程命令行三项。看错页面、旧 dev server、错误 worktree 或历史构建产物的截图一律作废。
- **整体图优先**：证明页面、弹窗、HUD、布局或游戏进行页时，主图必须是整页/整屏/整牌桌视图；局部近景只能作细节辅证。
- **满载态优先**：布局验收优先取元素最多、空间最紧、最能暴露遮挡/漂移/挤压的真实状态。没有满载态时，说明缺哪些对象并补独立证据。
- **过程需求给动态证据**：翻面、移动、结算跳分、转场、滚动、展开收起等时间维度需求，至少给动态证据或连续关键帧；不能只用最终静态图。
- **新 UI 覆盖矩阵**：新增、翻正或改变玩家可见/可操作界面时，登记 `新增项 -> 玩家动作/可见状态 -> 已有 E2E -> 需新增/修改 E2E -> 截图/断言证据`。已有测试只有直接命中操作步骤、断言和截图时才可复用。
- **基础浏览交互覆盖矩阵**：牌桌、棋盘、卡池、法术书或 loadout 进入实现验收时，覆盖矩阵必须同时列默认浏览态和规则操作态。默认浏览态最低覆盖：卡牌 / 对象能打开详情或放大检视；分类 / 筛选 / 分页能改变可见集合；地图 / 棋盘能拖拽、滚轮缩放或说明为什么无需自由查看；关闭检视后回到同一可操作页面。只覆盖计划、打出、提交或高亮目标等操作态，不足以证明基本流程可用。
- **假控件必须负向验收**：用户质疑“点不开 / 假的 / 没反应 / 只能看不能用”时，E2E 或截图证据必须直接点击对应控件并断言现实结果变化，例如放大层出现、筛选后卡牌集合变化、分页目标出现、视窗 transform 改变。只证明元素存在、按钮可见、class 改色、截图看起来像控件或其它阶段能点击，不得判通过。
- **重复 UI 要代码验收**：涉及候选比较、角色 / 阵营 / 配置选择、setup gate、摘要页、教程操作页或任何删除重复信息的 UI 改动时，不能只靠规范文字或人工看图防回归。验收必须包含代码级检索、静态断言、DOM 文本扫描或真实入口 E2E 断言中的至少一种，明确列出本轮不应重复的文本 / 属性 / 组件锚点，并让重复项重新出现时测试失败。若某些重复来自正式牌面图像本身，断言应只禁止额外 UI 复写，不把牌面原文当作违规。
- **平行 owner 副本要负向验收**：修正“查看对方公开信息”类问题时，验收必须同时证明主槽位 owner 已切换、返回后 owner 复原，并用代码检索、静态断言或 DOM 断言禁止旧平行副本锚点回归。只证明新增的观察提示、详情面板或额外区域可见，不证明视角切换合同成立。
- **重复 UI 归入规则集验收**：用户已指出或审计已确认的重复，先直接删除、合并或降到日志 / 详情 / 无障碍承载，再把回归防线归入既有重复类型规则集，例如身份 owner、连续数值 owner、数量 / 容量 owner、卡面字段复写、动作提示复写、骰子 / 结算结果 owner。不得为单张卡、单个截图、单个按钮或单次反馈新建清单；只有现有类型无法覆盖一个新的 UI 类型时，才扩展 `.spec/tools/scan-ui-duplicate-owners.mjs`、E2E helper 或等价项目工具，并说明它接管的是哪类重复机制。规则集必须写清同一状态下每条信息的唯一承载、允许进入日志 / 详情 / 无障碍的承载、禁止回到主可见层的文本 / 属性 / 组件锚点；以后同类 UI 改动复用或扩展既有规则集，不另造平行自查。
- **动作按钮与规则说明分工**：按钮的亮起 / 置灰只表达当前动作是否可执行，按钮正文不得重复渲染提示卡已经承载的 Token / 资源成本、使用门槛、次数限制或完整效果；这些信息可保留在提示卡、详情层和无障碍名称中。按钮保留动作短名称，按钮可用态必须继续绑定统一的领域可用性判断，不能通过删除成本文字来改变规则校验。
- **每个可见元素必须有唯一职责**：新增、保留或重构可见 UI 前，先判断这个元素到底承担哪一个玩家任务：识别当前对象、展示当前结果、提供下一步动作、承载玩家决策、显示等待状态、或进入历史 / 详情。说不出唯一职责，或职责已被同屏更强元素承担时，默认删除、收纳到详情 / 日志 / 无障碍文本，或合并进唯一承载位。随机 / 结算画面尤其要防重复：骰子本体已经表达点数，主合计已经表达总数，后续提示只能补“下一步要分配 / 确认 / 选择什么”，不得再次可见复写骰子数量、每颗点数、同一个合计、固定 0 加值或同一句规则描述。去重不等于删除规则原文承载；当前结算主体若离开原牌面或需要独立确认，面板必须保留一处事件描述 / 来源语境和一处实际效果；若来源对象已由卡面、日志、发现牌或同屏对象清楚承载，不强制也不得额外复写来源卡名标题。禁止的只是同一信息的第二处复写、派生数字和机制解释。此类去重必须配套至少一条代码级或 E2E 断言，证明被删除的重复承载没有回到可见主界面。
- **元素职责审计前置**：这不是“发现一个多余 UI 再删一个”的事。设计稿、真实 UI 或截图送验前，必须对当前画面的所有常驻元素做完整职责清单：元素名称、唯一玩家任务、是否来自规则 / 素材 / 成熟参考、若成熟参考没有为什么当前游戏必须有、若成熟参考有而当前游戏没有为什么可以缺省、是否可被本体点击 / 详情层 / 无障碍文本承接。没有完成这张清单时，不得用局部 DOM 通过、单个文案删除或少量截图宣告 UI 通过。
- **可逆选择验结果槽位**：修正或新增计划、组队、装备、骰子分配、目标分配等提交前可编辑流程时，验收必须覆盖已选结果所在槽位 / 队列 / 目标对象的真实取消路径：点击结果本体或其贴附移除入口后，已选数量、来源 id、进度按钮和可继续选择状态同步回退；再从原候选重新选择能恢复同一结果。若同时有放大 / 检视入口，必须负向证明点检视不改变已选状态，点结果本体不打开放大层。
- **目标高亮要验几何**：涉及 token、棋子、房间、卡牌、骰子、玩家板槽位或玩家目标的 UI 改动，E2E / 截图验收至少覆盖一个目标高亮的本体可见、主边界样式、中心贴合和尺寸差；矩形对象的高亮框应读取真实 `getBoundingClientRect()` 或等价几何证据，证明主边界四边与宿主本体四边基本一致，常规容差不超过 2px。非矩形对象、骰面、地图区域或玩家板槽位要提供等价几何证据，证明高亮归属清楚、不遮主体、不包进外挂信息。只检查颜色、元素存在或可点击不能证明视觉通过。
- **素材比例要验真**：截图或 E2E 声称素材通过时，至少对本轮关键素材抽查渲染比例：用 `naturalWidth / naturalHeight`、atlas frame 尺寸、裁剪配置或源图尺寸与屏幕上的 `getBoundingClientRect()` 比对。除规则上已批准的等比裁切外，肉眼可见拉伸、压扁、比例偏差或人物 / 卡牌变形都不能判 `PASS`；不能只用“图片加载成功”“DOM 存在”替代比例验收。
- **外挂信息不进高亮框**：高亮几何断言必须量对象本体表面，不量外层按钮、热区、角标、持有 token、状态徽章或观察按钮；若这些外挂信息被同一描边包进去，截图即使能点击也判未达标。
- **AI/自动玩家影响另列**：UI 改动若改变确认、取消、跳过、对象选择、响应窗口、阶段推进或并列合法动作，必须检查 AI/自动玩家是否仍能从规则动作合同枚举并执行同一批合法命令。
- **多态 UI 多态验证**：弹窗、菜单、开关、模式选择、重设、关闭、状态分支至少覆盖可见态、一个主交互后态和本轮直接影响的关闭/重置/下一步态。
- **移动/PC 对照要有矩阵**：涉及双端、手机横屏或响应式验收时，列 `PC 一级信息/交互、PC 承载、移动端去向、是否同源、证据、判定`；不能把 PC 关键决策信息直接消失后称为更清爽。
- **真实来源页优先**：视觉/对齐类 bug 的主证据必须来自原始来源页、真实路由、真实组件挂载位或真实业务链路；demo/playground/孤立组件图只能作辅证。
- **最终回复门槛**：只要本轮新增或暴露用户可见 UI，最终汇报必须点名真实入口 E2E、关键截图或真机证据；未跑通时只能写 `端到端未完成` 或 `blocked`，不得写完成。
- **截图不得隐藏流程**：端到端截图必须覆盖玩家真实操作前、操作后和下一可操作态；测试 harness、内部 dispatch、直接领域命令或状态替换完成的步骤不得作为截图中的“已完成流程”，只能作为起点构造或诊断证据。缺少可见玩家动作与结果对应关系时，截图不得判为流程验收通过。
- **流程图组按真实顺序命名**：端到端图组的主序号必须跟玩家动作顺序一致；同一流程中的后补截图要重排或另建新图组，不能保留“06 后跳 30、再回 07”这类会让审图者误判流程的编号。代表态、专题回归、移动端对照和诊断截图必须用独立前缀或 evidence 分组，不能混进主教程流。
- **测试干扰项例外回到 E2E 主源**：端到端为排除共享 FAB、聊天浮钮、调试入口或录屏控制等非流程悬浮工具而隐藏命中区时，以 [`e2e-verification`](e2e-verification.md) 的例外条款为准；游戏 HUD、阶段按钮、手牌、地图、目标、确认入口和当前提示仍不得被隐藏。
- **重复与独立步骤分开验收**：只有动作类型、承接对象、规则效果、权限条件和后续状态都完全相同的重复操作，才允许在 E2E 中批量压缩；每个独立的选择、确认、关闭、切换或阶段推进都必须逐次由真实控件完成。尤其是连续的阶段按钮，即使外观相似，也不得合并为一次点击或隐藏 dispatch。

## 连续流程与通用检视

- **无决策阶段自动推进**：阶段只执行系统结算、资源更新或动画，没有玩家可选决策时，流程必须在结算完成后自动推进到下一个需要玩家操作的状态；只有存在真实选择、响应窗口或并行确认时才显示推进动作。
- **检视入口统一**：需要玩家阅读的公开对象必须由统一检视能力承载：对象本体可点击或提供可发现的放大入口；放大层应复用共享检视组件，不能在各处发明不可见热区。
- **主操作与检视分区**：同一卡牌、单位、棋子、区域或玩家面板在当前状态下既能执行规则动作又能查看详情时，对象本体单击优先保留主规则动作；检视 / 放大必须落在独立图标、右键、长按或其它可发现的次级入口上。次级入口不得覆盖本体中心热区，也不得用透明层、父容器默认点击或 disabled 后 fallback 抢走主操作。验收必须分别点击本体中心和检视入口中心：本体中心产生计划 / 出牌 / 选目标等规则结果且不打开放大层，检视入口打开详情且不改变规则状态；E2E 不得用隐藏 helper、状态注入或点击其它子元素替代玩家可见的本体点击。
- **关闭不占内容槽位**：放大层关闭控件统一使用右上角叉号图标，按钮盒子叠在浮层边缘，不得在卡牌上方或正文流中预留一整行“关闭”文字按钮。关闭按钮仍须有可访问名称和至少 `44x44px` 命中区。
- **视窗只拖拽场景**：地图 / 棋盘自由拖拽的命中区必须是地图视窗本身，地图内容、格子、实体和特效共享同一变换父级；页面壳层、手牌、玩家面板和主动作栏不得跟随地图拖拽。拖拽后必须抑制误点击，并覆盖滚轮 / 触控缩放锚点；自由拖拽验收必须分别断言横向和纵向位移，不能只断言 transform 字符串改变。
- **无职责标题默认删除**：仅重复“竞技场 / 游戏模式 / 当前页面”且不承载规则状态或玩家动作的顶部标题，不得占用主舞台槽位；阶段与动作提示应贴近实际主操作承载，必要时使用无障碍或教程锚点保留语义，不保留视觉空壳。
- **阶段指示按交互模型裁决**：阶段轨道不是桌游 UI 的默认组件。只有阶段顺序本身是玩家决策信息、等待条件或回看依据时，才保留独立阶段指示器；否则使用贴近当前动作的上下文提示。不得因为其它产品有阶段轨道就复制到当前界面。
- **开放场景不套比例框**：地图、棋盘或画布是可平移、可缩放的场景时，视窗应占据页面 / 牌桌可用区域，场景内容作为独立变换层；禁止用 `aspect-ratio`、固定百分比容器或页面级缩放把场景锁成居中的小框。玩家状态、手牌 / 法术书、计划区、主动作栏等界面对象与场景分层，拖拽场景后界面锚点必须保持不变；界面锚点应像 Unity Canvas 锚点一样按真实视口的九宫格 / 边缘 / 中轴对齐，对齐是坐标关系，不是另套一层设计画布或固定比例内框来限制摆放。

## 联机与视角

- **局内 setup 独立承载**：会影响 seat、阵营、私有手牌、私有负载或共同投票的前置选择，默认在 match 内 setup 层完成；不得只放建房页，也不得压在正式棋盘 HUD 上。
- **在线 UI 绑定 viewer/seat**：非当前 seat 的手牌、私有 prompt、私有 setup 和私有候选默认不得出现在当前页；轮到别人行动时不能自动切成对方视角。
- **联机截图先锁页面归属**：联机截图必须说明来自房主页、玩家 A/B/C 页还是观战页。固定玩家连续体验的证据链必须固定同一 viewer，不能中途切席位拍图后命名成单玩家流程。
- **等待态只写等待语义**：等待别人行动时，只表达谁在行动、我在等谁、还差几项；不要把只对操作者有意义的步骤提示展示给等待方。

## 禁止行为

- 禁止新增 UI 后不走真实入口验证。
- 禁止用 mock 页面、示意图、局部组件截图或测试绿灯冒充端到端。
- 禁止用几何断言替代肉眼图面结论。
- 禁止为了让 UI 看起来对而改规则、素材、录入矩阵或测试基线。
- 禁止把单游戏专有机制、地区、势力、流程术语或截图口径写进通用 UI 规范；只保留抽象职责、分层原则和验收门禁。
