# UI/UX 总原则

适用于 UI 组件、布局、样式、游戏界面、交互一致性和视觉审查。本文件只保留长期通用原则；UI 改动门禁见 [`ui-change-gates`](ui-change-gates.md)，响应式见 [`ui-responsive-layout`](ui-responsive-layout.md)，动画见 [`ui-animation-patterns`](ui-animation-patterns.md)，生成稿落地见 [`generated-design-implementation`](generated-design-implementation.md)。

## 入口

- 修改 UI、样式、布局、交互壳层、截图验收、回归恢复或主交互槽位前，先读 [`ui-change-gates`](ui-change-gates.md)。
- 规则或素材驱动的 UI / 设计稿，必须先锁规则真相源、主体素材账本和素材输入链；不能先画容器再补证据。
- 用户要设计稿时，设计稿未获明确人工批准前不得进入真实页面实现、运行时 E2E 或截图验收。
- 固定构图类游戏先过 PC 主基线；PC 未通过时不得用移动端截图证明整体完成。
- 双端、手机横屏、board shell 或移动端同构问题，继续读 [`ui-responsive-layout`](ui-responsive-layout.md)。

## 审美原则

- **主体先行**：牌面、棋盘、地图、骰盘、手牌、token、角色和当前可操作对象是画面主体。界面不应先让玩家看到厚容器、说明框、边框墙或后台面板。
- **开放式牌桌优先**：对局主界面默认用对象自身边界、留白、尺度、光照和轻量分割线组织空间；只有规则确实需要窗口化承接时才用封闭容器。
- **深度分级**：核心结算和重点面板可用柔和阴影、轻玻璃或局部压场；高频更新、动画中和拖拽对象只用 `transform / opacity`，禁止毛玻璃和高成本滤镜。
- **动效克制**：关键交互和阶段变化可有 150-300ms 的状态反馈；高频点击、连续操作和密集列表只用颜色、透明度或轻微位移，不做复杂动画。
- **布局稳定**：临时提示、等待、响应、确认和浮层默认使用 overlay / HUD / portal，不插入正常文档流挤压棋盘、手牌、右 rail 或主按钮。
- **顶层 HUD 不避让场景实体**：玩家属性、提示卡、资源和同类常驻 HUD 是界面锚点层，不是棋盘 / 地图 / 单位布局的一部分；它们的左上、右上、左下、右下等锚点不得由底图内容、场上实体是否存在或当前地图缩放位置驱动。HUD 可以覆盖低权重底图纹理，但不能吞掉当前来源、目标、可选对象或主操作热区；提示卡、数值背景和纯视觉承载默认不吃输入，只有放大、关闭、切换、提交等真实控件命中。若 HUD 与当前玩家任务发生视觉或点击冲突，先处理层级职责、透明命中区、同层 HUD 重排、临时折叠或当前目标提权，不把 HUD 横向漂移去“躲”低层实体。
- **空间让渡要兑现**：压缩辅助区的目标是把空间交还给主内容；验收要证明主对象更完整、更可读或更少被裁切，而不只是辅助区数字变小。
- **信息簇对齐看外层锚点**：角色面板、玩家状态、提示卡、资源图标和同类 HUD 信息簇必须先贴近它服务的屏幕边、座位、角色或提示卡；“左对齐 / 右对齐”验收要检查整组外层边界、主对象和相邻读数之间的关系，不能只让内部图标列 `items-start`，同时用固定宽度、无职责留白或偏移把整组悬到无关区域。
- **主信息不因操作态降级**：玩家属性、资源、手牌 / 候选牌、计划 / 装备槽、场上单位和当前 prompt 这类主信息，不能因为进入选中、拖拽、确认、目标选择或教程态就自动缩成低可读版本。确需压缩时必须说明被让出的空间给了哪个主对象，并用截图或几何证据证明玩家任务更清楚。
- **几何不等于体验**：不重叠、DOM 存在、bbox 正确只能证明工程约束；玩家第一眼不知道看哪里、点哪里、结果在哪里，仍判 UI 未达标。

## 交互一致性

- **同类交互同语法**：同一游戏内的候选、选中、确认、跳过、目标选择、卡牌动作、数值徽章和高亮必须复用同一套主视觉语法；发现不一致时要扩审同类元素。
- **平台范式先复用**：同一平台内已有通过截图验收的同类交互时，先抽取其对象本体、外挂信息、点击热区和颜色语义的不变量，再迁入当前游戏；不得在同类目标选择、高亮或结果反馈上重新造一套相近但边界不同的 UI 语法。
- **对象本体优先**：真实对象已在画面可见时，点击区域应落在对象本体或贴合高亮上；文字按钮、编号、列表、圆点和代理块只能作备用、无障碍或无法定位对象时的入口。
- **选择结果落目标槽位**：玩家选择卡牌、单位、装备、计划、队伍、骰子或分配对象后，已选结果必须进入它最终要影响的槽位、队列、轨道或目标对象本体；角标、小标签、计数气泡和按钮文案只能辅助，不得替代“对象已经放到哪里”的主视觉承载。
- **可逆选择由结果槽位承接**：提交前仍可编辑的已选卡牌、单位、装备、计划、骰子或分配项，必须能从已选结果所在的槽位、队列或目标对象本体直接取消 / 移除，或有贴在该结果上的明确移除入口；不得强迫玩家回到原列表、原卡池或原对象再点一次才取消。若同一对象同时可检视，检视入口必须独立，不得抢结果槽位的取消 / 调整主操作。
- **高亮先给边界**：合法目标、可选对象和当前来源必须先让玩家看清“哪个对象 / 槽位 / 区域可操作”。同一游戏内优先沿用已验收的成熟语法；实线描边、背后描边、ring、发光、槽位覆盖或轻透明遮罩都可以成立，不强制绿色、实心或单一实线。高亮不得压住、缩小、裁切或改形对象本体；多层视觉只能有一个贴合本体的主边界，其它光晕、脉冲、阴影或填充只能辅助，不能变成离体的第二个目标框。
- **组合选择分步执行**：需要选择对象、目标、位置、数量或确认的动作，应按规则顺序逐步让玩家点真实对象；不要把所有组合提前展开成按钮墙。
- **按钮只承载按钮该承载的事**：按钮用于确认、取消、跳过、数量提交、模式切换或无对象语义分支；不要用按钮替代可点击对象本体。
- **决策靠近阅读对象**：确认、跳过、替代、抽取、使用等二选一/提交控件必须接在玩家刚阅读的规则对象、结果面板或主操作区之后；不得把按钮放到远离当前对象的位置，让玩家在屏幕上来回找归属。
- **小字不能当动作控件**：声明、跳过、确认、取消、下一步、筛选、模式选择等控件必须有可见按钮形态、状态反馈和足够命中区；弱标签只能作提示。
- **单行动作不得被内部换行破坏**：确认、提交、继续、返回、关闭、分页、筛选和模式切换等本应一行完成的按钮 / 标签，必须在所有目标视口保持单行；用 `white-space: nowrap`、内容自适应宽度或等价布局保证完整文案可见，并在 E2E / DOM 验收中检查实际计算样式与 `scrollWidth <= clientWidth`。只有规则文案、说明正文或明确设计为多行的控件才允许换行；不能靠把按钮高度撑大、截断文字或让玩家自行猜测来掩盖宽度不足。
- **提示不复读视觉**：当高亮、箭头、选中态、禁用态已经表达目标时，常驻文案只补动作意图、成本、结果或必要对象名，不再写“点绿色目标”这类复述。
- **图标状态要可解释**：只用图标、灰亮进度或数字叠层承载生命、资源、行动点、属性、buff / debuff 等状态时，必须提供玩家可见的 hover / focus 说明；`title`、`aria-label` 或测试属性只能作辅助，不能替代画面中出现的说明。说明层必须贴近图标、脱离正常布局流、不挤压主对象，并保留键盘 / 触控等价入口。
- **等待态单一**：非操作者或非 owner 页面只保留一处明确等待语义，不展示对操作者才有意义的 prompt 标题、候选壳层、禁用工具或重复按钮。

## 流程与视窗原则

- **系统结算与玩家决策分离**：只执行固定结算、资源更新或动画的阶段应由系统在完成后自动进入下一个需要玩家决策的状态；只有存在真实选择、响应窗口或并行确认时，才要求玩家操作推进。
- **阶段提示服从交互模型**：阶段指示器不是默认版式。是否独立展示阶段、展示多大、放在何处，取决于阶段顺序是否是玩家当前决策信息；直接由上下文动作驱动的流程以当前动作提示为主，不为装饰而增加常驻阶段轨道。
- **场景与界面壳层分离**：地图、棋盘、画布等可平移/缩放场景必须在独立视窗和变换层内处理输入；页面壳层、固定 HUD 和主操作区保持稳定锚点，拖拽场景不得带动整页布局。
- **开放场景不受小比例框限制**：当场景需要自由查看或内容尺寸超过视窗时，视窗应使用牌桌/页面的可用空间，不能用固定比例或百分比小容器把场景锁在居中小框内。
- **检视关闭控件不占正文空间**：详情、放大或临时检视层的关闭动作应叠加在层的右上角，使用清晰图标和足够命中区；不为“关闭”文字单独预留正文行。
- **无职责标题不占主舞台**：只重复页面、模式或场景名称且不承载状态、导航或动作的标题不应占据主舞台空间；需要的语义应由实际状态提示、无障碍名称或教程锚点承载。
- **多实体密排先保主体尺寸**：同一格、同一槽或同一队列需要显示多个可操作实体时，先定义稳定轴、席位 / 阵营锚点和最小可读尺寸，再决定横排、竖排、显式换列、分页、滚动或焦点放大。多阵营 / 多席位同格时要把“阵营分区轴”和“同阵营排列轴”分开裁定，例如先按席位左右分 lane，再让同席位对象在各自 lane 内上下分行排列；不得把用户说的“上下排列”简化成整组上下分区。除非规则或成熟同类 UI 明确采用叠牌语法，不能用负边距、绝对定位或错位压叠把多个可操作单位硬塞进同一容器；当同一 lane 的稳定可见预算允许多列时，优先定义每列容量并显式换列，再考虑滚动、分页、展开列表或焦点检视，不得把单位、卡牌或 token 横向挤成看不清的小片。

## 组件来源

- 新增 UI 控件前先搜索现有同类组件、同游戏 `ui/` 目录、`src/components/**`、`src/hooks/ui/**` 和设计系统；已有能力能扩展时不得另起重复实现。
- 同一功能在每个游戏中默认只有一个主组件：卡牌展示、卡牌详情、参考卡放大、prompt 选择、行动日志、撤回等场景都应复用既有组件或共享能力。
- 视角、席位或观察对象变化时，优先让既有角色板、公开牌堆 / 弃牌、持有区、装备区、手牌区或状态区切换数据源；只有原槽位规则上不可见、权限不同或尺寸不足时，才允许新增只读详情承载，并必须证明不是同类功能副本。
- 查看对手 / 队友公开归档、公开持有物、装备或公开区域时，默认交互是先切换观察对象或公开视角，再让同一主槽位显示目标 owner 的数据。不得为了“能看见对方信息”在当前视角并排复制第二套同类牌堆、持有区、装备区或状态区；只有规则要求双方公开信息同步比较时，才允许并列展示，且必须写清比较任务和退出条件。
- 操作日志和撤回统一由 `GameHUD` / FAB、`ActionLogSystem`、`UndoProvider` 等共享入口承载；游戏 Board 不再重复实现完整日志面板、撤回面板或最近操作列表。
- Inspect / 放大镜按钮必须与实体状态层分离：不要挂在会被 `ring / shadow / opacity / grayscale / scale / rotate` 影响的同一 DOM 层。
- 共享 FAB / 界面锚点按面板类型分流：短提示面板贴当前按钮，长日志/滚动面板贴展开列或按钮列 reference；改共享锚点时至少检查短面板和长面板。

## 文案边界

- 玩家 UI 只写当前产品状态、规则对象、可执行动作、成本、结果和必要状态；不要把实现原因、审计结论、测试语言、字段名、素材来源、真相源状态或开发解释写给玩家。
- 正式素材已包含标题、类型、规则正文、点数或结果说明时，运行时 UI 只补交互控件、归属、无障碍文本和必要状态；看不清先修裁切、压缩、尺寸或放大承接，不另写一套可见正文替代素材。
- 缺素材不是玩家状态。正式对局缺图时，玩家 UI 最多用牌背、对象名和类别临时承接；缺口进入 intake、manifest、evidence 或开发日志。
- Toast 只写一句结果或错误；详细原因、过程和后续说明放日志、帮助或可展开详情。
- 后台、工作台、管理界面和终端用户可见文案默认自然中文；保留英文术语必须有稳定理由或用户明确要求。
- 可见正文最低字号 `12px`；如果文字只是装饰且不需要读，改成非文字装饰或删除。

## 加载与状态

- 正式图片对象加载中默认用与目标轮廓一致的扫光 / shimmer；禁止裸露纯色块、静态空框或错误占位冒充正式对象。
- 扫光只表示“正式图片对象正在加载”，不能用于未来空槽、尚未出现对象、流程预留位或装饰骨架。
- **未发生对象不占位**：如果规则结果是未抽牌、未生成 token、未结算事件、未获得物品或某对象被跳过，主舞台必须退回当前牌桌、下一步入口或轻量反馈；不得为了“说明没发生”再显示结果面板、牌背、黑卡、空卡框、素材缺失框、未来对象槽位，或已经被跳过的触发符号/触发对象。
- 首帧依赖正式图集、牌背、地图、骰子皮肤或阻塞式结果时，必须等关键素材就绪，或显示明确 loading / 扫光；不得先闪默认样式再跳正确样式。
- UI 派生状态默认从权威游戏状态、路由、配置或服务端快照直接派生；确需同步到 Context / React state 时，写入前比较签名，内容不变不得 setter。
- 视觉可用态必须绑定真实业务语义，如领域 `validate(...)`、统一可用集合或查询函数；组件不得凭局部条件复制一套近似判断。
- 触发方式和可用语义分离：设备差异可以改变“怎么触发”，不能改变“当前是否可用”的视觉真相来源。

## 通用 Hooks

位于 `src/hooks/ui/`，新增交互行为前必须先搜索复用。

| Hook | 用途 | 口径 |
| --- | --- | --- |
| `useHorizontalDragScroll` | 横向卡牌 / 对象横排浏览 | 用于横向列表滚轮转横向与拖拽；数据表和日志表仍保留普通上下滚动。 |
| `useTouchLongPress` | 触控长按 | 提供移动取消和长按后 click 抑制。 |
| `useTouchInspectGesture` | 触控预览 | 长按预览，同时保留 tap 主动作。 |
| `useArmedActivation` | 触控先选中再激活 | 粗指针设备需要先 armed 再执行时使用。 |
| `useDeferredRender` | 延迟渲染 | 避免首帧闪烁。 |
| `useDelayedBackdropBlur` | 延迟毛玻璃 | 动画期间延后启用高成本效果。 |

## 技术护栏

- Flex 纵向滚动子元素必须同时有 `flex-1 min-h-0 overflow-y-auto`；横向滚动用 `min-w-0`，避免内容被父级裁剪而非滚动。
- UI 只负责展示与交互；业务逻辑放引擎/系统/领域层，manifest、常量、资源清单和文案 key 用数据文件维护。
- 动态提示使用项目 z-index 常量或明确语义层，禁止随手写更大的裸 z-index 掩盖遮挡问题。
- board shell 内需要锚定真实视口的 HUD / Overlay / Loading 必须通过 HUD portal 或等价视口锚点脱离缩放容器；普通 Board 根容器跟随壳层高度，不读取原始 viewport 高度。

## 游戏 UI 范式

- 游戏 UI 必须遵守 `design-system/game-ui/MASTER.md` 和对应风格文件；风格 token、对象语法和交互语义优先于临时组件审美。
- 可交互元素必须有 hover / press / focus / disabled 反馈；禁用态要让玩家知道“不可用原因”或至少看出不可执行。
- 重大阶段变化必须有一次性可感知事件和短状态，不靠日志、角落小字或内部状态让玩家猜；详细规则进入规则书、帮助层或阅读器，不塞进常驻主 UI。
- 伤害、治疗、资源变化、控制权变化等结果反馈必须绑定受影响对象本体，不能只靠日志、侧栏数字或攻击者动效。
- 绑定对象本体的飘字 / 跳字只承载短结果，例如数值、恢复、受伤、获得或失去；详细属性名、长原因和多句说明不能跟着飘字上屏。
- 长文阅读界面内容优先：规则书、读本、帮助、故事档案把主空间留给正文；翻页、关闭和页码贴边轻量承载，不抢正文空间。
