# Show Image To User

## 单一职责

本 skill 定义“把本地图片、GIF 或录屏展示给用户本人看”的项目入口。技能名保留历史名称；录屏 / 视频展示不另建第二入口。

- 截图是否具备 E2E / UI 验收资格，不在本入口定义。
- AI 自己读图、核图和 `PASS` / `REVISE`，不在本入口定义。
- 大图安全读取、降采样和裁切，不在本入口定义。
- 本入口不维护第二套截图验收正文；它只裁决选哪张图、用什么用户展示通道、失败时怎么回报。

项目约定：

- 主证据目录：`test-results/evidence-screenshots/<game>/<测试文件>/<用例>/`。
- 候选图、失败图、中间排查图不能冒充最终验收图；它们只能作为路径或诊断材料报告，不允许打开给用户看。
- 服务器相册不是默认交付。只有用户明确要求上传、发布链接、服务器相册或手机查看时，才允许发布到 `http://8.148.71.102:18080/#/boardgame/<task-id>`。
- 获得上传授权后，只允许更新 `/home/admin/image-preview/data/projects/boardgame/tasks/<task-id>/`，禁止改预览站壳层、根路由或客户端代码。

## 开图时机（强制）

- 打开图片 / 录屏只在三类情况下发生：① 用户当轮明确要求看图、打开图、截图验收、录屏或玩家视角检查；② 本轮交付物本身被任务合同定义为图片型设计稿、视觉验收图、动效验收录屏或最终有序图组；③ 本轮已经完成 UI / 游戏画面 / 截图验收收口，且已经选定最终 `PASS` 图片、图组或录屏。其它场景即使已经生成截图 / 录屏、补了 evidence、AI 自己核图 `PASS`，也默认只汇报路径、截图 / 录屏清单和核图结论，不自动打开查看器。
- 录屏、GIF 和视频属于同一类用户可见验收物：只有用户明确要求看实际动效 / 录屏 / GIF，或本轮交付物被任务合同定义为动效验收媒体时，才允许展示。未达到本轮 `PASS` 前，不得把录屏或动图当过程材料打开给用户。
- 打开图片 / 录屏是上述图片型或动效型交付的完成信号，不是排查过程动作。实现、测试、截图 / 录屏链、AI 核图或证据选择还没完成时，不得调用 PureRef、系统查看器或 Codex App 内联展示；最多报告候选路径、缺口和下一步。
- 用户说 `图呢`、`我看看` 或类似表达时，先判断是否已经具备最终验收图、最终有序图组或最终动效录屏：具备则展示；不具备则先补实现、补 E2E、补截图 / 录屏链或补核图。禁止为了回应催图而先打开旧图、单张候选图、过程图、诊断录屏或截图目录。
- 同一轮同一份媒体或同一组媒体只展示一次。展示通道成功后，除非用户明确说没看到、打开错图、要重开或要改用另一通道，否则不得重复调用查看器。
- **最终 PASS 前禁止开图 / 录屏（强制）**：本条只在已经触发“用户可见展示”时生效。本轮截图、录屏、过程图、候选图、诊断图、失败图、过期图和历史图，只要尚未被当前验收流程选为最终交付物并明确判定 `PASS`，一律不得通过 PureRef、系统查看器、Codex App 内联图、会在对话中渲染图片的 `view_image` / `Viewed Image` 预览或服务器相册展示给用户。用户明确要求“先打开看看 / 打开失败图 / 打开候选图 / 我看看”也不能绕过；正确动作是继续验收、说明尚未通过，或只给路径与未通过原因。若本轮没有触发用户可见展示，则不需要为了满足本条而主动展示 `PASS` 图或录屏。
- **PASS 只看本轮要求（强制）**：最终 `PASS` 的判断对象是用户本轮明确交给你的要求，不是整页 UI、全游戏完成度或其它顺手发现。展示前必须先写出“本轮要求清单”，每一项都要有直接证据并标为 `PASS`；任一项未达标、缺证据或被用户刚指出仍不对，都不得展示。非本轮要求的问题可以记录为备注或后续项，但既不能阻塞本轮展示，也不能拿来替代本轮要求的达标证据。若非本轮问题会让本轮截图 / 录屏无法证明目标要求，例如遮住目标、截图不是目标状态、录屏没有覆盖目标动作或流程没有触发，则它按“本轮证据无效”处理。

## 一步到位开图流程

用户要求看图、打开图或最终截图验收时，只允许按这条正向顺序执行一次：

1. 锁定本轮展示要求清单，并判断需要单图、有序图组还是录屏。
2. 完成当前工作树、当前入口、当前目标状态的截图 / 录屏与必要测试；若需要重跑、补图、同步目录或重建证据，必须在开图前完成。
3. 选定最终原图 / 原录屏；多图时先用项目唯一标记脚本生成 `00-sequence-index.png` 和无遮挡标记副本。
4. 创建或更新只覆盖本轮要求的 `PASS` 清单，确保清单里的测试结果、原图路径、标记图路径和当前证据运行一致。
5. 先用 `open-verified-image.mjs --dry-run` 校验清单和路径；发现旧图、缺图、标注遮挡、清单不匹配或验收项不足时，回到第 2 步修正，不得先打开再补救。
6. dry-run 通过后，用同一份 `PASS` 清单和同一组媒体调用一次真实查看器；这次打开就是本轮用户可见交付。

完成第 6 步后，除非用户明确说没看到、打开错图、要重开或切换通道，否则不得再次调用 PureRef / 系统查看器 / 内联展示。同一轮中如果开图后才发现截图、清单或标注不是最终状态，这次开图必须按展示失败处理；修正后只能在说明前次作废的情况下重建完整链路，不能把多次打开包装成正常过程。

## 触发条件

这些表达都表示用户要看见图片本身：`打开图片`、`打开图`、`图呢`、`给我看图`、`截图呢`、`我看看`、`重新打开`。
这些表达表示用户要看见动态媒体本身：`录屏`、`动图`、`GIF`、`视频`、`看实际效果`、`看动画效果`。动态媒体仍必须先满足本轮 `PASS` 清单；录制文件存在不等于允许展示。

- 用户明确要看图时，先判断最终 `PASS` 是否成立；成立才完成用户可见展示，再解释。未成立时不得展示，只能继续补验收或说明阻塞。
- 工作流已经选定最终验收图、最终有序图组或最终录屏，且 AI 核图通过时，如果本轮属于 UI / 游戏画面 / 截图验收收口，必须以 `task-final-delivery` 完成用户可见展示；不要等用户再追问“图呢”。若只是过程截图、诊断截图、候选截图或非视觉任务附带截图，仍只能报告路径和结论。
- 用户只要求“给路径 / 证据路径”时，只给绝对路径，不打开查看器。
- `E2E passed`、`截图已生成`、`录屏已生成`、`证据已更新`、`我需要看一下图` 不是打开本地查看器的充分授权。用户明确要看图 / 录屏、本轮交付物就是图片型 / 动效型验收物，或本轮已经完成 UI / 游戏画面 / 截图最终验收并选定 `PASS` 验收图时，才进入展示流程；进入后仍必须等最终验收物 `PASS` 才允许展示。
- 已经在上一轮或上一专题收工、打开或明确降级为独立证据的图组，不得因为新一轮修其它问题而重新打包展示。新一轮只需要引用这些证据时，报告路径和既有结论即可；只有用户重新要求看该专题，或本轮目标本身重新打开该专题验收，才允许创建新的用户展示清单。

## 选图规则

- 选图必须匹配当前目标：PC / mobile / 横屏 / 当前游戏 / 当前流程不能靠宽泛关键词或最新时间戳乱配。
- 修代码、样式、数据后要看当前效果时，默认先重拍当前工作树、当前入口、当前目标状态的新图；旧图只能标为历史证据。
- 单图只能证明单帧。翻页、前后态、PC/移动对照、弹窗开关、流程步骤或分支状态默认交付最小有序图组。
- 原图优先：用户说 `原图`、`未压缩`、`压缩前`、`原始截图` 时，禁止打开缩略图、裁切图、OCR 图、contact sheet 或压缩预览。
- 验收图默认用真实原始截图；标记副本只作为多图顺序辅助，必须保留并汇报原始路径。
- 如果最新相关图是失败、过期或诊断图，只能报告路径和失败原因，不得打开；需要继续补实现、补截图或重新验收直到出现最终 `PASS` 图。
- 用户点名只看某个编号之后、某个章节、某个分支或“后续流程”时，必须先按该范围生成新的标注图组和 PASS 清单；不得用更大的历史 PASS 清单顺手打开前置图、辅助图、移动端对照图或诊断图。局部图组第一张必须说明从哪个真实流程点接起；如果接下来进入专题 / 代表态 / 视角分支，用户可见标题必须写明分段起点，不能让连续编号暗示自然承接。

## 展示通道

BoardGame 默认展示顺序：

1. PureRef：静态图片和 GIF 的默认用户展示通道，Codex App / Codex desktop 也一样。
2. Windows / 系统查看器：视频 / 录屏默认用系统查看器；PureRef 不可用、未保持运行或无法接收图片时也使用系统查看器。
3. Codex App Markdown 内联：只有用户明确说“在这里打开 / 内联展示 / 发在对话里”，或外部查看器都失败时使用。

执行要求：

- 一次交付只选一个用户展示通道；一个通道成功后，不要再重复打开同一组图。
- 多图用 PureRef 时必须一次性传入整个路径数组，禁止每张图各启动一次 PureRef。
- 多图交付后必须写清顺序映射，例如 `1. PC 选择态：事件牌 + 骰盘 + 属性选项`，不能只说“打开了 4 张图”。
- `view_image`、OCR、缩略图、裁切图、contact sheet 只有在宿主不会把图片渲染给用户时才可作为 AI 自检；一旦宿主会在对话、任务面板或外部窗口中展示图片，就按用户展示处理，必须满足最终 `PASS` 门槛。若没有私有看图通道，未 `PASS` 候选只能用非展示型机器检查、路径和文字证据推进，不能为了 AI 自检先打开。
- 给用户看图不等于 AI 验收；AI 核图必须另写图面事实和 `PASS` / `REVISE` 结论。

## 多图标记

PureRef 打开多张最终验收图时，默认先生成带序号的全尺寸标记副本：

```powershell
python ".spec/skills/show-image-to-user/scripts/label-image-sequence.py" `
  --out-dir "<evidence-dir>\_labeled-for-pureref" `
  --title "交互流程截图顺序" `
  --image "<absolute-image-path-1>" --label "万箭齐发卡牌：打牌前" --transition "起点：攻击已选中，卡牌仍在手牌" `
  --image "<absolute-image-path-2>" --label "万箭齐发卡牌：卡牌特写" --transition "从 01 打出万箭齐发 -> 弹出卡牌特写，并显示首次奖励骰结果描述"
```

- `.spec/skills/show-image-to-user/scripts/label-image-sequence.py` 是项目内唯一标记脚本；它生成 `00-sequence-index.png` 和 `NN-labeled-*`，标注说明只能放在扩展画布或独立索引里，禁止覆盖原始截图像素。
- 标记副本必须保持原始截图完整可见；如果序号、标题、说明栏、遮罩或水印压住了游戏画面、牌面、教程卡、按钮、地图、骰子或其它验收对象，该标记副本只能作诊断废图，不能进入 PASS 清单、不能打开给用户，也不能替代原图验收。
- PureRef 多图默认打开顺序：`00-sequence-index.png` 在前，后接 `01-labeled-*`、`02-labeled-*` 等，路径顺序必须和可见编号一致。
- 标记图里所有用户可见标题、步骤标签、承接说明和补充说明必须使用中文；原始文件名、代码文件名或测试名可以保留作证据，但不能替代中文说明。
- 标签必须写玩家能懂的步骤和对象类型，例如 `卡牌`、`技能`、`响应窗口`、`骰盘`，不能只写文件名、测试名或内部字段。
- 每张图从第二张开始必须说明相对上一张发生了什么；第一张必须说明起点或前置状态。
- 用户明确要求不加标记时，打开原图，但仍提供有序映射；必要时可另开独立序列索引。

## 执行入口

单图：

```powershell
node scripts/verify/open-verified-image.mjs --pass-manifest "<本轮要求达标清单.json>" --viewer pureref --path "<单张最终原图绝对路径>"
```

录屏 / 视频：

```powershell
node scripts/verify/open-verified-image.mjs --pass-manifest "<本轮要求达标清单.json>" --viewer system --path "<最终录屏绝对路径>"
```

多图：

```powershell
node scripts/verify/open-verified-image.mjs --pass-manifest "<本轮要求达标清单.json>" --viewer pureref --paths "<00-sequence-index.png>" "<01-labeled-*.png>" "<02-labeled-*.png>"
```

- `scripts/verify/open-verified-image.mjs` 是查看器执行入口；它负责解析路径、调用 PureRef / 系统查看器并回报结果；实际开图 / 开录屏必须显式传 `--pass-manifest`，否则脚本拒绝执行。
- `--pass-manifest` 指向的 JSON 必须只覆盖本轮用户要求，最低结构为：`verdict: "PASS"`、`scope: "current-user-request"`、`display: { "purpose": "final-user-visible-delivery", "trigger": "user-requested-open" | "task-final-delivery", "viewer": "pureref" | "system", "finalPassBeforeOpen": true }`、`requirements: [{ requirement, status: "PASS", evidence: [...] }]`、`images: [...]` 或 `media: [...]`。脚本会校验每项要求都是 `PASS`、证据非空、展示目的为最终用户展示，并且本次打开的图片 / GIF / 视频全部在清单中；这防止用“过程核图 / 我确认过了 / 泛化 UI PASS”代替本轮最终达标。
- 查看器入口会记录最近 50 次成功打开的 PASS 清单和媒体列表；同一份清单或同一组媒体默认拒绝重复打开。只有用户明确说没看到、打开错图、要重开或要改用另一通道时，才允许在同一命令后追加 `--force-reopen`。
- PASS 清单必须覆盖截图可理解性所依赖的关键画面对象：如果最终图组里可见的卡牌、法术、技能、装备、附件、单位或牌库 / 法术书是本轮流程、动画来源、目标或上下文承载，必须有证据说明这些牌面 / 素材已经真实渲染、不是空白壳层或纯色占位。关键牌面空白时，不管动画像素、E2E、文件路径或脚本开图是否成功，都不得创建 `PASS` 清单，也不得打开给用户。
- 多图、`--paths`、`--path` 重复参数一律直接调用上述 `node` 入口；不要通过 `npm run verify:open-image -- --paths ...` 转发参数，避免 npm 把 `--paths` 或图片路径解析成自己的参数并产生误导性 warning。
- 脚本成功只证明打开动作已发起并有进程/命令结果；用户说没看到、打开错图、图被标注遮挡、只有一张或图为空时，按展示失败处理。若问题来自最终图或标记副本本身不真实，必须撤销本轮 PASS 清单并重新生成无遮挡图组；不得用同一清单重开。
- Codex App 内联只能使用绝对本地路径：`![说明](D:/absolute/path/image.png)`；路径含空格时用 `![说明](<D:/path with spaces/image.png>)`。

## 收口门禁

发送最终回复前做三问：

0. 本轮是否明确触发用户可见展示：用户要求打开 / 看图 / 截图验收 / 录屏 / GIF / 看实际动效，任务交付物本身就是图片型 / 动效型验收物，或本轮已经完成 UI / 游戏画面 / 截图最终验收并选定 `PASS` 验收图？
1. 本轮是否已经选定最终用户验收图、最终有序图组或最终动效录屏？
2. AI 是否已经对同一张原图、同一组原图或同一份录屏给出通过结论？
3. 同一轮是否已按本 skill 完成 PureRef / 系统查看器 / 明确内联展示，或给出展示失败证据？

如果 0 为否，不主动调用查看器；只汇报截图清单、路径、核图结论或 evidence。若 0、1、2 为是而 3 为否，禁止收口；先展示再汇报。子 agent 可以协助找图、核图、生成标签或执行查看器命令，但父 agent 负责当前用户可见回复，不能把子 agent 私有消息、`view_image` 预览或路径当成用户已看到。

## 失败处理

- 路径找不到：先列目录核实，再用解析后的绝对路径重试。
- 文件来自截图工具：先确认存在且大小非零。
- PureRef 未安装、未保持运行或未接收图片：转系统图片查看器。
- 复用 PureRef 失败并开出新进程：汇报前后进程 ID，不说“已复用旧窗口”。
- 内联图未渲染：改走 PureRef / 系统图片查看器。
- 两类外部查看器和内联都失败：汇报目标路径、文件是否存在、尝试过的通道、最小补救动作。
